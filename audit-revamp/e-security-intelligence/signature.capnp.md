# Audit — signature.capnp (433 lines)

## Verdict
**FIX (targeted).** Correct instincts are present and worth preserving: `SignRequest.payload @0 :T.DataHandle` (`:212`), `SignedContents.payload @2 :T.DataHandle` (`:61`), the unbounded `trustedIssuers @2` explicitly deprecated in favour of `trustedIssuersPaginated @6` (`:134-139`), and `VerifyError` wrapping `T.Error` (`:193-197`). Against that, the file's two algorithm enums collide **by name** with `crypto.capnp`'s — same names, divergent ordinals — which is the batch's most serious latent wire hazard; every `verify*` method takes inline `Data` while every `sign` method takes a handle; and an entire interface (`RevocationList`) plus two request structs are unreachable.

## Wire-breakers
No ordinal collisions on `SignatureService` (@0–@14, `:129-178`). Three reachability/type hazards:
- **Enum name collision with divergent ordinals.** `signature.capnp:98-110` `SignatureAlgorithm` (ed25519 **@0**, ecdsaP256 @1, ecdsaP384 @2, rsaPkcs1 @3, rsaPss @4, mlDsa44 @5, mlDsa65 @6, mlDsa87 @7) vs `crypto.capnp:610-635` `SignatureAlgorithm` (rsaPkcs1Sha256 **@0**, …, ed25519 **@12**, …, mlDsa44 **@24**). And `signature.capnp:114-125` `HashAlgorithm` (sha256 **@0**) vs `crypto.capnp:263-296` `HashAlgorithm` (sha224 **@0**, sha256 **@1**). Neither file imports the other, so nothing fails to compile today — but `ValidProof.algorithm @2 :SignatureAlgorithm` (`:190`) and `SignResult.algorithm @0 :SignatureAlgorithm` (`crypto.capnp:664`) are both "the algorithm that produced this signature", and the ordinal 5 means `mlDsa44` in one schema and `ecdsaSha256` in the other. Any service, log, or stored message carrying a bare algorithm ordinal across that boundary is misread with no error raised.
- `signature.capnp:351-361` `RevocationList` is **unreachable** — no method in any schema returns it; consequently `RevocationSubscription` (`:374-377`) is unreachable too.
- `signature.capnp:261-272` `MultiSignRequest` and `:289-302` `ThresholdSignRequest` are **dead** — no method accepts them, while `aggregateSignatures @7` (`:148`), `verifyMulti @8` (`:152`), `verifyThreshold @9` (`:156`) exist with no producing path.

## Duplicates & overlaps
- `SignatureAlgorithm`/`HashAlgorithm` ↔ `crypto.capnp:263-296`, `crypto.capnp:610-635`, `biometric.capnp:231-241` (with divergent ordinals — see Wire-breakers).
- `Certificate` ↔ `crypto.capnp:823-838` `CertificateInfo`.
- `keyId :Data` ↔ `T.KeyId` (`types.capnp:1041`) and `T.KeyFingerprint` (`types.capnp:1062`), the latter documented as this file's intended type.
- `RevokedKey`/`RevocationList` ↔ `capability.capnp`'s revocation (`revoke @4`, `revokeControlled @9`) and `key_management.capnp`'s `KeyStatus.revoked`/`revokeKey @4` — key revocation now has three homes.
- `AttestationData` ↔ `key_management.capnp:99` `attestation` and `runtime_search.capnp:192-199` `AttestationRequirement`.
- `AlgorithmNegotiation` (`:381-390`) ↔ `crypto.capnp:855-901` `AlgorithmSpec`/`SupportedAlgorithms` and `speech.capnp:456-474` codec negotiation — three negotiation contracts.
- `maxChainDepth` const at `:53` duplicates the intent of `SigningRule.maxChainDepth @4 :UInt32` (`:426`), one as a constant and one as a per-rule field, with no declared precedence.

## Gaps & holes
- **No signing-key lifecycle.** `SignRequest.keyId @1 :Data` (`:213`) is a fingerprint with no path to renew, rotate, or discover it — `key_management.capnp` owns lifecycle and this file never references it. A signer cannot learn that its key was revoked without polling `RevocationList`, which is itself unreachable (`:351`).
- `verify` returns `VerifyResult` (`:180-185`) with `valid :ValidProof` / `invalid :VerifyError` — good — but `VerifyError` is only reachable through the *invalid* branch, so "verification could not be attempted" (unknown algorithm, malformed input) is encoded as `unknownAlgorithm @3`/`malformed @4` (`:203-204`) with no way to carry the underlying `T.Error` cause.
- `aggregateSignatures @7` (`:148-149`) returns a single `Signature` with no threshold metadata, so a verifier cannot tell how many signatures it represents or what the threshold was — `MultiSignature` carries that data (`:248-259`) but is not linked to the aggregate.
- `revocation` is defined here but unreachable (Wire-breakers), so revocation *is* implemented only in `capability.capnp` and `key_management.capnp` — with two different key identities (`Data` here, `T.KeyId` there) that cannot be correlated.

## Zero-cost & eco
The sign path is correct and the verify path is not — that single asymmetry is the file's whole R2 story (five methods, see the table). `batchVerify @14 (payloads :List(Data))` (`:176`) is the worst case: N payloads copied into one message on the path designed for bulk verification.

## UX & implementer guidance
- `TrustEvent.custom @4 :CustomTrustEvent` (`:232-233`) is a struct with `typeId @0 :UInt64; payload @1 :Data` (`:236-239`) — the `UnknownEvent` shape, but named `custom` and used only for trust events. This is the right primitive with the wrong name; the schema already contains the pattern the doctrine asks for.
- `Certificate.issuerKeyId @5 :Data` (`:80`) is documented as "Fingerprint of the signing certificate (this one's issuer)" — the name says "issuer key id", the value is a fingerprint, and no algorithm accompanies it.
- `Signature.issuer @0 :Text` (`:30`) is a free-form label used for trust matching (`TrustedIssuer.name @0 :Text`, `:221`) — string equality is the trust decision, so a typo in an issuer label silently changes who is trusted.
- `Signature.encoding @3 :Text` ("cbor", "json", "capnproto", `:63`) is an open encoding hint with no declared default, so two backends may produce signatures over different canonical encodings of the same payload that both verify against themselves and fail against each other.

## Recommended actions
1. **Eliminate the enum collision: import or re-declare against `crypto.capnp`'s enums once they are open tokens (see the crypto report), and use one spelling there.** Gain: closes the silent ordinal misinterpretation — the most serious latent wire defect in the batch; cost: this file's two enums are deleted and their fields change type.
2. **Make the verify path take `T.DataHandle`** (`verify`, `verifyMulti`, `verifyThreshold`, `verifyWithRevocation`, `batchVerify`). Gain: verification stops being a copy cliff and matches the already-correct sign path; cost: five signatures.
3. **Adopt `T.KeyFingerprint` for `keyId` fields.** Gain: fingerprints become self-describing (the `types.capnp:1064` "use length as heuristic" hack disappears) and keys become correlatable with `key_management`/`crypto`; cost: field type changes at six sites.
4. **Make `RevocationList` reachable (or delete it with `RevocationSubscription`), and delete `MultiSignRequest`/`ThresholdSignRequest`.** Gain: no dead contract; cost: one accessor method, or three type deletions.
5. **Open `AttestationFormat` to a `Text` token.** Gain: any platform's attestation becomes reportable instead of `custom`; cost: consumers switch on strings.
6. **Unify certificate representation with `crypto.capnp`** (one typed `Certificate`/`CertificateInfo`, or a handle). Gain: `verifyCertificateChain` and `Signature.chain` stop needing an undefined conversion; cost: one type is deleted.
7. **Declare the canonical encoding default for `SignedContents.encoding @3`.** Gain: cross-backend signature verification stops failing on encoding disagreement; cost: one comment plus a conformance token.
