# Audit — crypto.capnp (902 lines)

## Verdict
**REWRITE.** The interface shape is right — hash/hmac/kdf/random/aead/asymmetric/wrap/import-export/certificates/streams is the correct surface, and the request-side zero-cost discipline is correct (keys, nonces, plaintexts and ciphertexts are all `T.DataHandle`, `:143-145`, `:528-531`, `:545-547`, `:212-217`). But the schema's *organising principle* is the failure mode the doctrine names: roughly 130 algorithm values across eight closed enums, every one naming a technology, all in required positions. The file proves the failure itself by having already been amended — the NIST FIPS 203/204/205 post-quantum additions at `:521-522`, `:591-604` and `:868-885` are exactly the "additive only forever" tax (`TIMELESSNESS.md:96`). Patching individual enums leaves the architecture; the rewrite keeps the methods and changes every algorithm field to an open token.

## Wire-breakers
No ordinal collisions (`CryptoService` @0–@29 unique, `:19-137`; all struct ordinals collision-free) and all `T.*` references resolve. Two *latent* wire hazards and one dead type:
- `signature.capnp:98-110` `SignatureAlgorithm` and `signature.capnp:114-125` `HashAlgorithm` carry the **same names** as this file's `:610-635` and `:263-296` enums with **divergent ordinals** — `ed25519` is `@12` here and `@0` there; `sha256` is `@1` here and `@0` there; `mlDsa44` is `@24` here and `@5` there. Neither file imports the other, so nothing fails to compile today — but a service, a log line, or a stored message that carries a bare algorithm ordinal across that boundary is silently misread. This is the batch's most serious wire hazard.
- `crypto.capnp:499-505` `RandomRequest` is **dead**: no method takes it. `randomBytes @6 (length :UInt32)` (`:47`) and `randomBytesBuffer @7 (bufferId, offset, length)` (`:50`) re-declare its `useBuffer`/`bufferId`/`offset`/`length` fields as parameters.
- `T.HashOutput` (`types.capnp:1179-1182`) was promoted with an explicit "cross-schema impact" note naming `crypto.capnp HashResult.hash` (`types.capnp:1171-1173`) — this file returns raw `Data` at `:307`. The migration documented in `types.capnp` never happened here.

## Duplicates & overlaps
- **The header's central claim is false in its own body**: `:12-13` says "Deduplicates crypto bits from auth.capnp, biometric.capnp, signature.capnp, key_management.capnp" — but `biometric.capnp:231-241` keeps `SigningAlgorithm`, `signature.capnp:98-125` keeps `SignatureAlgorithm`+`HashAlgorithm`, `key_management.capnp:49-72` keeps `KeyAlgorithmFamily`+`KeyExportFormat`, and `secret.capnp:229-240` keeps its own `DeriveKeyRequest`. The consolidation is asserted, not performed.
- `HashAlgorithm` (`:263-296`) ↔ `signature.capnp:114-125` `HashAlgorithm` (different values, different ordinals).
- `SignatureAlgorithm` (`:610-635`) ↔ `signature.capnp:98-110` and `biometric.capnp:231-241`.
- `KeyFormat` (`:742-751`) ↔ `key_management.capnp:63-72` `KeyExportFormat` (different value sets) ↔ `vcard.capnp:519-524` `KeyType`.
- `DeriveKeyRequest` (`:385-414`) ↔ `secret.capnp:229-240` `DeriveKeyRequest` (same name, different fields — an import of both is ambiguous).
- `CertificateInfo` (`:823-838`) ↔ `signature.capnp:68-85` `Certificate`, with a third representation as raw `der :List(Data)` at `:96`.
- `constantTimeCompare` (`:101`) ↔ `secret.capnp:103` `compareSecrets`.
- `wrapKey`/`unwrapKey` (`:77`, `:80`) ↔ `secret.capnp:108-113` `wrapSecret`/`unwrapSecret`.
- `AlgorithmSpec`+`PostQuantumSpec` (`:855-885`) restate information already in `AsymmetricAlgorithm`/`SupportedAlgorithms`.

## Gaps & holes
- **No key-rotation or key-compromise contract in the crypto layer.** `signature.capnp:351-377` has a `RevocationList` interface; `key_management.capnp` has rotation; this file — the one that signs and encrypts — has nothing. A backend that discovers a key is compromised has no protocol path to signal it to signers/verifiers, so revocation is per-schema and inconsistent.
- `createDrbg @26`/`DrbgHandle`/`CreateDrbgRequest` (`:125`, `:179-200`) create a stateful protocol object whose reseed semantics (`reseedInterval @3`, `:187`) are declared as a number with no behaviour attached — an implementer must invent when a reseed is forced and what happens to a DRBG used past it.
- `generateKeyPair` returns `privateKey @2 :Data` "Only if backend supports export" (`:648`) — the "if" is invisible on the wire: a caller cannot distinguish "export unsupported" from "export produced nothing" without out-of-band knowledge of the backend.
- No contract for `nonce` uniqueness enforcement: `EncryptRequest.nonce @2 :T.DataHandle` is documented "Must be unique per key!" (`:529`) as a comment. A backend that receives a reused nonce has no way to refuse it in a typed way, and the AEAD failure it will eventually produce has no dedicated code.

## Zero-cost & eco
The single most important finding in this file is the request/result asymmetry: inputs are handles, outputs are copies. That, plus `randomBytes`'s inline return, is the whole R2 story. `HashStream`/`HmacStream`/`EncryptStream`/`DecryptStream` (`:316-325`, `:148-175`) are the right streaming shape, but each interface's `update @0 (data :Data)` and `finalize -> (… :Data)` copies every chunk — the streaming APIs exist to avoid buffering, and then force it.

## UX & implementer guidance
- `AsymmetricAlgorithm` mixes *key types* (rsa, ecdsa, ed25519, mlKem) with *padding schemes* (rsaPssSha256, rsaOaepSha256, `:582-589`) in one enum, so `generateKeyPair` and `sign` share a vocabulary in which "rsa2048" and "rsaOaepSha256" are not the same kind of thing. An implementer must decide which of the two a given field wants.
- `KeyUse` (`:768-774`) and `SignRequest.prehashed @3`/`hashAlgorithm @4` (`:657-658`) both constrain usage, with no declared relationship.
- `HwAcceleration.provider @1 :Text` with examples "AES-NI, ARMv8 Crypto, Intel QAT, NVIDIA GPU" (`:900`) is a hint field naming vendors — harmless, but it is the kind of doc comment that becomes an enum.
- `hashStream`/`hmacStream` exist alongside `hash`/`hmac` with no guidance on when a stream is required, so two backends will accept different maximum inline sizes for the non-streaming path.

## Recommended actions
1. **Rewrite every algorithm field as an open token.** Concretely: `algorithm :Text` (or `T.MimeType` for key formats) plus a `parameters :T.StringMap` carrying the algorithm-specific knobs (`iterations`, `memoryKib`, `keySize`, `outputLength`), with `getSupportedAlgorithms` reporting the same open spellings. Gain: new constructions become requestable and interoperable with a schema change and no new ordinal — closing the amendment loop this file has already entered once; a backend can finally be asked for an algorithm it supports. Cost: consumers switch on strings (they can publish `const` conformance tokens exactly as `ai.capnp:600-622` does), and `AlgorithmSpec`/`PostQuantumSpec` collapse into the same open form. **This is the single highest-value action in the batch.**
2. **Move every result-side payload to `T.DataHandle`** (`EncryptResult.ciphertext`, `DecryptResult.plaintext`, `HpkeSealResult.ciphertext`/`encapsulatedKey`, `HpkeOpenSuccess.plaintext`, `KeyAgreementResult.sharedSecret`, `DeriveKeyResult.key`, `UnwrapKeyResult.key`, `randomBytes`, `drbgGenerate`). Gain: encrypt/decrypt stops copying bulk payloads twice and random generation stops being message-capped; cost: callers must read a handle, which is the pattern already used on the request side of the same methods.
3. **Make the stream interfaces handle-based on both directions** (`update (data :T.DataHandle)`, `finalize -> (… :T.DataHandle)`). Gain: streaming stops forcing buffering; cost: one field type per interface.
4. **Collapse the duplicate vocabularies with `signature`/`biometric`/`key_management`/`secret` into one open token set owned here.** Gain: removes the ordinal-collision wire hazard and four parallel crypto vocabularies; cost: four other files' field types change — several of which need changing anyway (see those reports).
5. **Delete `RandomRequest` (or use it).** Gain: removes a dead type that reads like a contract; cost: one struct, or two method signatures.
6. **Adopt `T.HashOutput` for hash results and `T.KeyFingerprint` where fingerprints appear.** Gain: makes two documented `types.capnp` promotions real and gives "which algorithm produced this" a home; cost: two field types.
7. **Add typed error reporting to `VerifyChainResult`.** Gain: chain failures stop being string-parsed; cost: one typed enum (or reuse `signature.capnp:199-208` `VerifyErrorCode`).
8. **Declare DRBG reseed behaviour and private-key-export visibility.** Gain: two invented-semantics forks close; cost: one comment each.
