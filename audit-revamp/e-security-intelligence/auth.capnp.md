# Audit — auth.capnp (443 lines)

## Verdict
**FIX (targeted).** `DESIGN_PRINCIPLES.md:540` judges this file a "Clean contract" — that verdict is wrong. The file contains the most severe security defect in the batch (`refreshToken` mints a fresh token from a token *id* alone, with no proof of possession), a second authorization system that the doctrine explicitly forbids, a plaintext-password wire representation, and three-way duplication with `access.capnp` and `biometric.capnp` of MFA, lockout, and credential enrollment. What it does have going for it: pagination on every list, typed scope ids, and honest result unions (`AuthResult`, `EnrollResult`, `AuthEvent`).

## Wire-breakers
None. Method ordinals @0–@25 unique (`:17-83`); struct ordinals collision-free; all `T.*` references resolve. One **name collision with a different shape**: `MfaChallenge` (`:271-276`) vs `access.capnp:465-476` `MfaChallenge` — same name, different fields (`type :AuthMethodType` vs `method :MfaMethod`). A file importing both has two types by one name, and `AuthResult.mfaRequired @2 :MfaChallenge` (`:129`) refers to a different struct than `UnlockOutcome.mfaRequired @3 :MfaChallenge` (`access.capnp:419`).

## Doctrine violations

## Duplicates & overlaps
- **MFA, three ways**: `auth.capnp:271-276` `MfaChallenge` + `startMfa @11`/`verifyMfa @12` (`:46-47`) vs `access.capnp:465-476` `MfaChallenge` + `requestMfaChallenge @11`/`verifyMfaChallenge @12` (`:615-616`) vs `biometric.capnp:131-147` `AuthPrompt`. Two complete MFA flows in two schemas of one batch, with different challenge payloads and different method vocabularies.
- **Lockout, four ways**: `auth.capnp:302-307` `LockoutStatus` + `LockoutKind` (`:309-315`); `access.capnp:397-406` `LockoutInfo` + `LockoutKind` (`access.capnp` has no `LockoutKind`); `biometric.capnp:110-119` `LockoutInfo` + `LockoutKind` (`:121-127`). `LockoutKind` is byte-identical in `auth.capnp:309-315` and `biometric.capnp:121-127` — two enums, same name, same values, two files.
- **Credential enrollment, twice**: `auth.capnp:280-298` `EnrollRequest`/`EnrollResult`/`EnrollSuccess` vs `access.capnp:611` `enrollCredential @9` + `RecoveryCode`/`BackupCredential` (`access.capnp:236-270`).
- **Claims duplicated inside the file**: `ClaimsSet` (`:166-185`) restates `AuthToken`'s own `issuer`/`audience`/`expiresAt`/`notBefore`/`issuedAt` fields (`:150-154`) with the same names, one struct nested inside the other.
- `AuthFactor.id @0 :T.AuthMethodId` (`:259`) — an auth *factor* is identified by an auth *method* id, conflating two concepts; `getSupportedFactors @6` (`:37`) returns factors keyed by method ids.

## Gaps & holes
- **No credential-recovery contract.** `auth.capnp` owns `enrollCredential @13` and `revokeToken @8`, but recovery lives only in `access.capnp` (`RecoveryMethod`, `RecoveryCode`, `startRecovery @23`, `submitRecoveryCode @24`). An auth backend that is not the device lock — a remote service, a headless node, a network identity provider — therefore has **no recovery contract at all**. Demonstrated fork risk: every non-device auth backend must invent recovery, and the protocols will not interoperate. This is the file's most consequential hole after `refreshToken`.
- `refreshToken` has no rotation/revocation-of-old-token contract: whether the old token is invalidated by a refresh is unstated, so replay of a stolen old token is backend-dependent.
- `lockout` and rate-limiting exist only as observations (`getLockoutStatus @14`, `:53`) with no policy input — a backend cannot declare its lockout policy through this file; `access.capnp:355-370` `LockoutPolicy` does that, so auth consumers must poll device-lock policy to learn about auth lockouts.
- `validateClaims @22` / `ClaimsSchema` (`:73`, `:404`) embed a JWT-shaped validation contract; `ClaimsSchema.requiredScopes @4 :List(T.ScopeId)` (`:414`) is typed, but `requiredFields @0 :List(Text)` (`:406`) is a free-form field-name list with no vocabulary.

## Zero-cost & eco
No bulk payloads — this file deals in small secrets, so `Data`/`Text` are defensible for them. Two eco notes: `AppIcon.data @0 :Data` (`:235`) should be `T.DataHandle` (icons exceed 1 KB easily and the protocol has the type); `AuthSubscription.pull @0 () -> (events :List(AuthEvent))` (`:320`) is unbounded with a `cancel` but no pagination.

## UX & implementer guidance
- `AuthResult.custom @4 :Data` (`:131`) is an opaque error escape inside a union that already has a typed `failed @1 :T.Error` — two ways to report failure, and `custom` carries no discriminator.
- `TokenType.capability @1` (`:189`) invites the exact confusion the doctrine guards against: an auth token shaped like a capability, verified by a different mechanism (`introspectToken @18`, `:61`), sitting beside `capability.capnp`'s real capability. `DESIGN_PRINCIPLES.md:463` cites "a distributed system might use a JWT" as evidence the capability system is backend-agnostic — but `AuthToken.value :Data` (`:147`) reintroduces the JWT as a first-class protocol object.
- `LockoutKind` (`:309-315`) distinguishes `permanent`, `timed`, and `temporary` — three values with no declared difference between them. An implementer cannot choose.
- `enforceAuthMethodPriority @21 (methodId, minPriority) -> (enforced :Bool)` (`:70`) returns a boolean from a method that changes no state and whose name promises enforcement it does not perform.

## Recommended actions
1. **Require proof of possession to refresh**: `refreshToken` takes the current token value (or a signed challenge) alongside the id, and validates them. Gain: closes an unauthenticated session-extension path — the batch's most severe single-line security defect; cost: callers must hold the token value, which they already do.
2. **Delete `PermissionRequest`/`PermissionGrant`/`PermissionCheck`/`checkPermission` and express grants as `Capability`s** (the `types.capnp:1518` `PolicyId` promotion already anticipates this). Gain: one authorization system, and auth grants gain attenuation/revocation/delegation that the current model cannot express; cost: two method signatures and the removal of a second access model consumers currently straddle.
3. **Make `Credentials`' secret fields opaque `Data` rather than `Text`, and gate `enrollCredential` behind a capability.** Gain: secrets stop being greppable text in a message arena, and enrollment stops being open to non-holders; cost: callers must materialise `Data` for a password.
4. **Unify MFA and lockout across auth/access/biometric.** The canonical owner should be one of them — `access.capnp` owns the state machine and the recovery flow, so it is the natural home, with `auth.capnp` delegating. Gain: three MFA flows and four lockout structs become one each; cost: two files' method signatures change.
5. **Use `T.ScopeId` in `AuthSuccess.grantedScopes`.** Gain: one scope vocabulary per file instead of three; cost: consumers resolve the id (the registry at `:76-82` already exists for that).
6. **Add a recovery contract for non-device auth backends** (recovery methods and codes belong in this file, with `access.capnp` delegating for the device-lock case). Gain: remote and headless identity providers get an interoperable recovery path instead of inventing one; cost: a small set of types shared with access.
7. **Define `revokeAllTokens`' blast radius in the schema.** Gain: two backends stop revoking different amounts; cost: one comment.
