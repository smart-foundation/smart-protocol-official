# Audit — vcard.capnp (703 lines)

## Verdict
**FIX (targeted).** `MERGE-INTO-contacts` is the wrong answer and this file should be kept: vCard (RFC 6350) is an *external* standard that will exist in 2046 regardless of what this protocol does, so a dedicated converter contract is one of the more timeless things in the tree, and the file's payload handling is correct (`VCardPhoto.data`, `VCardSound.data`, `VCardKey.data`, import/export data are all `T.DataHandle`). The defects are: a 1998 TYPE vocabulary frozen into two enums while the open parameters mechanism sits two structs away, a missing conversion contract with `contacts.capnp` (which already owns import/export), and a schema-registry half that describes a standard the consumer can already read.

## Wire-breakers
None. Method ordinals @0–@11 unique (`:30-70`); `VCardContact` fields @0–@33 and `VCard` @0–@2 collision-free; all `T.*` references resolve. One duplicate enum **name** across files: `ConflictResolution` (`:667-672`) is identical to `calendar.capnp:423-428` — same name, same values, two schemas; a file importing both has two types by one name.

## Doctrine violations

## Duplicates & overlaps
- **`VCardContact` (`:348-406`) duplicates `contacts.capnp:162-198` `Contact`** — name/emails/phones/addresses/photo/org/birthday/title/role/note all modelled twice. More importantly, **the conversion is undefined**: `contacts.capnp:19-20` already owns `exportContacts @19`/`importContacts @20` with `format :Text`, and this file owns the same operations with structured requests (`:32`, `:35`). Neither declares the field mapping (does `Contact.type = organization` produce `FN` or `N`? which `EmailEntry.type` maps to `TYPE=INTERNET`?). Fork risk: two implementers produce different `Contact`s from the same vCard.
- `ConflictResolution` (`:667-672`) ≡ `calendar.capnp:423-428`.
- The vCard sync block (`getSyncToken @7`, `syncChanges @8`, `resolveConflict @9`, `:56-62`) duplicates `calendar.capnp:65-71` (`getSyncToken @20`, `syncChanges @21`, `resolveConflict @22`) — same shape, different id types, two files.
- `KeyType` (`:519-524`) vs `key_management.capnp:63-72` `KeyExportFormat` vs `crypto.capnp:742-751` `KeyFormat` — three key-format vocabularies in the batch.
- `ExpertiseLevel` (`:553-560`, five levels), `HobbyLevel` (`:569-574`, three), `InterestLevel` (`:579-588`, three) — three enums for "how good at X" with different scales; a consumer cannot compare them and an implementer must invent the conversion.

## Gaps & holes
- **The `VCardContact` ↔ `Contact` mapping contract is absent** (above). This is the file's decisive gap: without it, import/export is not interoperable and every backend pairs them differently. A `fieldMapping :T.StringMap` exists on `ImportRequest`/`ExportRequest`/`FormatRequest` (`:86`, `:169`, `:236`) but its keys are undeclared — it is an escape hatch standing where a contract should be.
- `validateProperty @11 (property, version) -> (valid :Bool, errors :List(T.Warning))` (`:69`) returns a bare `Bool` plus warnings instead of a `T.Error`, so a caller cannot distinguish "invalid" from "could not check".
- `getPropertySchema @10` / `VCardPropertySchema` / `PropertyDefinition` / `RequiredProperty` / `CustomNamespace` (`:66`, `:676-702`) — the schema-registry half describes an external standard the consumer can already read, and the demonstrated fork risk is low. It adds six types and two methods to answer a question already answered by RFC 6350.

## Zero-cost & eco
Pass: `VCardPhoto.data @0 :T.DataHandle` (`:417`), `VCardSound.data` (`:423`), `VCardKey.data` (`:512`), `ImportRequest.data`/`ExportSuccess.data`/`FormatSuccess.data`/`parseVCard` all `T.DataHandle` (`:76`, `:197`, `:248`, `:38`). `VCardXml.content @1 :Data` (`:596`) is raw XML — should be `Text` or `T.DataHandle`; it is a payload, not an opaque token. `VCard.rawLines @2 :List(Text)` (`:287`) is correctly open for round-tripping unknown properties, which is the right instinct.

## UX & implementer guidance
- The header (`:16-28`) claims "contacts.capnp currently has no vCard support" — which was true when written, but `contacts.capnp:19-20` now has import/export. The comment is stale and actively misleading: it tells a reader the two files do not overlap, when they are the file's central unresolved overlap.
- `ImportRequest.duplicateHandling @3 = update` and `merge @4 :Bool = false` (`:82-83`) overlap (`DuplicateHandling.merge @3`, `:99-104` exists) with no declared precedence — two knobs controlling one decision.
- `ExportRequest.lineLength @6 :UInt16 = 75` with the comment "75 per RFC" (`:171`) hard-codes a formatting rule of a 1998 spec; harmless but it will be copied as a constant into implementations that then break on non-75-folded input.
- `VCardTimezone.offset @1 :Text` and `VCardTimezone.vtimezone @2 :Text` (`:495-502`) — a full VTIMEZONE blob as raw text; round-trippable, but there is no typed offset.

## Recommended actions
1. **Write the conversion contract**: a declared field mapping between `VCardContact` and `Contact` (or a single canonical converter interface that both files delegate to). Gain: import/export becomes interoperable instead of per-backend — this is the file's entire reason to exist; cost: a table in the schema plus the removal of one of the two overlapping import/export surfaces. If the mapping cannot be declared, `contacts.capnp`'s `format :Text` import/export should be removed rather than left as a second, vaguer contract.
2. **Delete `VCardPropertyType` and `TelephoneCapability`; use the open `parameters`/`types` `List(Text)` mechanism uniformly.** Gain: 2046 property parameters become expressible and one spelling replaces three (`VCardAddress.types`, `VCardEmail.types`, `VCardTelephone.types`); cost: consumers switch on strings — which they already do for addresses and emails.
3. **Delete `KeyType`; rely on `VCardKey.mediaType`.** Gain: one spelling for key type, and an open one; cost: none, the field already exists.
4. **Remove `VCardVersion.v50`.** Gain: stops asserting a standard that does not exist and makes `getSupportedVersions` honest; cost: none (the ordinal is preserved anyway, which is the doctrine's rule).
5. **Replace `VCardDateTime` with `T.Date`/`T.Timestamp` plus a timezone `Text`, and delete `GenderValue`'s `none`/`undefined` pair.** Gain: birthdays interoperate with `contacts.capnp` without a parser; cost: a struct simplification.
6. **Trim the schema-registry half** (`getPropertySchema`, `VCardPropertySchema`, `PropertyDefinition`, `RequiredProperty`, `CustomNamespace`, `validateProperty`) unless a consumer needs it. Gain: a converter contract instead of a self-describing registry; cost: any consumer of those six methods — there are none.
