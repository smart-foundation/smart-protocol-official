# audit: `schema/capture.capnp` (484 lines)

## Verdict
**FIX (targeted).** capture.capnp has the right payload instincts — `captureOutput`/`captureWindow`/`captureScreen`/`captureRegion` all return `T.DataHandle` (capture.capnp:29-31, 47) and `CaptureThumbnail.data` is a `T.DataHandle` (capture.capnp:247) — and its `CaptureSourceRef` union (capture.capnp:133-144) is a genuinely good replacement for an enum-plus-raw-id. But it contains the batch's clearest example of a contract that **cannot be used**: `startStream @12 → (streamId :T.CaptureId)` (capture.capnp:50-51) returns an id and the file declares "consumers read from the stream handle" (capture.capnp:232-233) while providing no method to read a frame, and `getCapture @8 → CaptureInfo` returns no pixel data. So batch, session, scheduled and streamed captures produce handles whose data can never be fetched. A second, independent problem is `CapturePermission` (capture.capnp:352-365) — screen/window/audio allowed flags and a source list, i.e. the permission-flag model DESIGN_PRINCIPLES.md:399 explicitly forbids. The rest is a normal accumulation of Audit-8/9 orphans and an unbounded `pull`.

## Wire-breakers
- **No compile errors, no ordinal collisions** (verified mechanically).
- `capture.capnp:50-51` — `startStream @12 (source, format) -> (streamId :T.CaptureId)`. The `CaptureStream` struct (capture.capnp:234-239) is described as "Returned by startStream; consumers read from the stream handle", but `startStream` returns a `T.CaptureId`, **not** a `CaptureStream`, and neither `CaptureStream` nor any frame-reading method is referenced anywhere. The continuous-capture contract is unusable as written.
- `capture.capnp:114` — `subscribeTranscode @38 (transcodeId :UInt64)`, but `transcode @15 → (transcoded :T.DataHandle)` returns **no transcode id**. So `TranscodeProgress.transcodeId`, `getTranscodeProgress`, and `TranscodeSubscription` reference an identifier no method produces. Dead contract, same class as `CaptureStream`.
- `capture.capnp:33-36` vs `capture.capnp:67-72` — recordings and sessions have different id types and different control sets (`T.CaptureId`/`UInt64 sessionId`), and `stopSession @21`/`pauseSession @22` take `UInt64` while `createSession @20` returns `CaptureSession` — a client gets a struct with `sessionId :UInt64` and passes the same number back; workable, but nothing says the number inside the struct is the handle.

## Duplicates & overlaps
- `WatermarkRequest`/`WatermarkPosition` (capture.capnp:203-217) ≡ camera.capnp:291-305 (verbatim).
- `CaptureRegion` ≡ camera.capnp `PrivacyRegion` ≡ `T.Rect`.
- `CaptureFormat` vs camera.capnp `CameraFormat` and camera.capnp's `PhotoOptions`/`VideoOptions` — three format descriptors for overlapping jobs.
- `AudioCaptureConfig` vs audio.capnp's `AudioFormat`/`T.PcmFormat`.
- `CapturePermission`/`setCapturePermission` vs audio.capnp's `MicAccess`/`MicPolicy`/`requestMicAccess` — two, mutually incompatible consent models for "may this app record".
- `shareCapture @28` vs media.capnp:73 `shareMedia` vs location.capnp:84 `shareLocation` — three share methods with the same `T.DeviceId`-as-target shape and none with a capability.
- `RetentionPolicy {maxAge, maxCount, maxSizeBytes, archiveAfter}` (capture.capnp:262-267) vs backup.capnp's retention and storage.capnp's quota — three lifecycle-policy shapes.
- `analyzeCapture @25 → CaptureAnalysis` (OCR + objects + faces) vs camera.capnp's `detectFaces`/`detectScene` — two analysis result shapes, one of which includes OCR.

## Gaps & holes
- **No data path for streams/batches/sessions** (the R8 row above). Concrete fork: every backend ships either a shared-memory frame ring of its own design or a per-frame RPC, and clients cannot be written portably.
- **No consent gate for the one thing that needs it most.** Screen capture of another app's windows is the classic sensitive operation; `setCapturePermission` is a flag struct, not a capability, and there is no method to *request* consent (contrast audio.capnp:73 `requestMicAccess` and audio.capnp:157 `requestMicAccess`).
- **No frame-dropping/quality contract for continuous capture.** `CaptureFormat.quality @4 :UInt8` and `frameRate :T.FrameRate` are requested values; nothing states whether the backend drops frames under load, whether it notifies, or whether `frameRate` is a target or a guarantee. A 2046 consumer cannot build a latency budget.
- **`getSources @9` is paginated but untyped** — no way to ask "which sources are capturable *right now*" (an occluded window, a protected output) without reading `CaptureSourceRef.custom @4 :Text` (capture.capnp:139) and guessing.
- **`listAnnotations @30 (captureId)`** returns all annotations unbounded with no pagination, though the schema otherwise paginates everywhere.
- **`negotiateFormat @34 → FormatNegotiationResult`** has a `rejected @1 :T.Error` variant (good), but `CaptureFormat` straddles video format and audio/watermark/cursor options, so "negotiation" mixes encoder capability with post-processing wishes.

## Zero-cost / eco
- **Correct:** one-shot captures return `T.DataHandle` (capture.capnp:29-31) and thumbnails are `T.DataHandle` (247). Where the data path exists, R2 is satisfied.
- **`CaptureEventSubscription.pull @0`** is unbounded (see R7) — the server-side queue is unbounded too, so a long unpulled recording grows memory without limit. The `pullPaginated @2` variant exists but every other schema in the batch treats pagination on a live stream as wrong (see the sensor audit): a live event stream has no offset. The right shape is a max-count pull, as in ai.capnp:276-277.
- **`stopRecording @4 → (data :T.DataHandle)`** (capture.capnp:34): the same whole-recording-in-one-result defect as camera.capnp:38, with the additional cost that the *entire recording* is now held in memory by the capture service until the client pulls.
- **Serialisation of `CaptureInfo` in `listCaptures @7`** ships `format :CaptureFormat` (which itself contains `audio`, `watermark`, `region`) and a `thumbnail` — a data-heavy struct repeated per capture with no summary form.
- **`createPipeline @17 → (pipelineId :UInt64)`** and `applyPipeline @18 (captureId, pipelineId) → (processed :T.CaptureId)` — pipelines are re-applied per capture with no caching, so a repeated 4K pipeline re-runs the full chain; nothing expresses pipeline state.

## UX & implementer guidance
- `CaptureSourceRef.screen @0 :Void` is "Default/full screen capture" while `captureScreen @2` exists as a separate method taking no source — two spellings of the same operation (one-shot vs session).
- `captureOutput @0 (outputId :T.OutputId, format)`, `captureWindow @1 (windowId :T.WindowId, format)`, `captureScreen @2 (format)`, `captureRegion @11 (outputId, region, format)` — four near-identical one-shot methods differing only in source; a `CaptureSourceRef` parameter would collapse them (the union already exists and is used by the session/stream methods).
- `applyPipeline @18 → (processed :T.CaptureId)` reuses `T.CaptureId` for a *derived* capture with no provenance field linking it to the input, so a pipeline result is indistinguishable from a fresh capture.
- `SharePreview.thumbnailMime @4 :Text` (capture.capnp:322) — a bare Text MIME where `T.MimeType` exists.
- `CaptureInfo.thumbnail @9 :CaptureThumbnail` is embedded in every `CaptureInfo` returned by `listCaptures`, so listing captures ships thumbnails the caller may never look at.

## Recommended actions
1. **Give `startStream` a readable stream**: return a `CaptureStream` interface (`pull (maxBytes) → frame` with `pixels :T.DataHandle`, `sequence`, `cancel`) instead of a bare id, and add a `readCapture (captureId, range)` path so batch/session/pipeline results are fetchable. Gain: makes five methods' outputs usable and removes the per-backend frame side channel. Cost: one interface + one method; ordinals free.
2. **Replace `CapturePermission` with capabilities**: split `CaptureService` into an ungated discovery half (`getSources`, `listCaptures`) and a capability-gated capture half (ai.capnp:578-584), dropping `screenAllowed`/`windowAllowed`/`audioAllowed` and the embedded `appId`. Gain: removes the forbidden permission flags and the self-granting hole. Cost: an accessor layer.
3. **Fix the subscription**: one `pull (maxCount)` with `T.SubscriptionResult`-style `ok/empty/ended/error`, delete `pullPaginated`'s offset semantics from a live stream. Gain: bounded memory, honest end-of-stream, no offset-into-a-stream trap. Cost: one signature.
4. **Add error unions to `shareCapture`, `addToPlaylist`-style creators, `transcode`.** Gain: honest failures. Cost: one struct each.
5. **Delete the four orphan types** (`CaptureStream` as a struct, `CaptureDeduplication`, `CompressionOptions`, `CaptureDeviceMetadata`) or wire them into methods. Gain: removes dead contract that misleads implementers into thinking the features exist. Cost: 4 deletions or 4 parameters.
6. **Collapse the four one-shot `capture*` methods into one taking `CaptureSourceRef`,** and unify `CaptureRegion`/`PrivacyRegion` on `T.Rect`, `AudioCaptureConfig` on `T.PcmFormat`. Gain: a smaller, single-spelling surface. Cost: three method deprecations (ordinals preserved).
7. **Add `unknown @N :UnknownEvent` + a payload to `CaptureEvent`.** Gain: stream errors become reportable rather than an empty enum value. Cost: one variant.
