# audit: `schema/bluetooth.capnp` (686 lines)

## Verdict
**FIX (targeted) — with one wire-level defect that makes the schema unusable as written, plus a resolved finding to report honestly.** The reported ordinal collision (`AuracastBroadcast.name @1` vs `deviceAddress @1`) **does not exist in the current file**: `broadcastId` is @0, `name` is @1 (bluetooth.capnp:310) and `deviceAddress` is @2 (bluetooth.capnp:312). I verified every struct and interface in all 19 assigned schemas mechanically for ordinal reuse and found none. Classify that report as **already absent / not present in this revision** — it cost nothing to check and must not be "fixed" into existence. The real defect in the same file is worse: **the schema uses two mutually unreachable representations of a device address.** `BluetoothDevice.address` is a `Text` MAC string (bluetooth.capnp:63), while every method that takes a device — `getDevice @7`, `pair @12`, `connectProfile @16`, all GATT methods, `provisionMeshNode @40` — takes `T.DeviceAddress`, which is `struct DeviceAddress { id @0 :UInt64 }` (types.capnp:37), an *opaque* UInt64 with no relation to the Text MAC. There is no method that maps a Text address to a `T.DeviceAddress`, so a client that scans cannot call any method on the device it found.

## Wire-breakers
- `bluetooth.capnp:510, 517-518, 521-524, 527-528, 529-530, 533-549, 552, 573` vs `bluetooth.capnp:63` — every device-taking method requires `T.DeviceAddress` (UInt64); the device descriptor exposes `address :Text`. `PairingEvent.address @0 :T.DeviceAddress` (415), `ConnectionEvent.address @0 :T.DeviceAddress` (652), `GattEvent.address @0 :T.DeviceAddress` (667) and `AuracastBroadcast.deviceAddress @2 :T.DeviceAddress` (312) all compound it. **Consequence: a scan result cannot be used.** A 2046 client gets `BluetoothDevice.address = "AA:BB:CC:DD:EE:FF"` and there is no API — `getDevice`, `pair`, `connectProfile`, `readCharacteristic` — that accepts it. This is a total contract break for the primary use case, and it is not a style issue: either the descriptor must expose `T.DeviceAddress` or the methods must accept the Text address (plus a private-address-aware resolver).
- `bluetooth.capnp:75, 106, 119, 129, 590` vs `bluetooth.capnp:152, 368` — service UUIDs are `List(Text)` in `BluetoothDevice.uuids`, `AdvertisementRecord.serviceUuids`, `AdvertisementRecord.solicitServiceUuids` and `ScanFilter.serviceUuids`, but `List(BluetoothUuid)` in `ServiceDataEntry.uuid` (152) and `GattServiceFilter.uuids` (368). Two spellings of one identifier with no defined Text form ("0x180D"? the full 128-bit hyphenated string?). A filter written one way will not match a record read the other.
- `types.capnp:768-770` — `struct BluetoothAddress { address @0 :Text; }` exists and is used by **nothing** (verified by grep). The protocol already has a typed Bluetooth address, and bluetooth.capnp ignores it in favour of raw `Text`. Dead type plus an unmet need.

## Duplicates & overlaps
- `T.BluetoothAddress` (types.capnp:768) vs `BluetoothDevice.address :Text` — a typed address exists and is unused.
- Service UUID as `Text` in 5 places vs `BluetoothUuid` in 2 (see Wire-breakers).
- `BluetoothProfile` vs audio.capnp's `AudioTransport`/`CodecFamily` (a2dp/hfp are named in both vocabularies).
- `AudioCodecId`/`AudioChannelMode` vs audio.capnp's `CodecFamily`/`ChannelLayout`/`ChannelMode` — **a third and fourth channel-layout/codec vocabulary** in the batch.
- `LeAudioConfig { groupId, rank, location, availableContexts, supportedContexts, volume, microphoneMute }` (bluetooth.capnp:219-234) vs audio.capnp's `LeAudioConfig`-shaped fields (`setPerRoleDuckLevels`, `ChannelLayout`) — the LE-Audio location/context bitmasks exist only here, with `UInt8 volume @5` (0-255) against audio.capnp's `Float32` volume convention. Two volume scales.
- `BondState`/`BondSubscription` vs `BluetoothDevice.paired/connected/bonded/trusted @4-7` (bluetooth.capnp:68-71) — four independent boolean bond dimensions plus a separate bond state machine.

## Gaps & holes
- **No inbound pairing contract.** `PairingEvent` (bluetooth.capnp:414-421) is **referenced by no method** (verified by grep) — nothing returns it. So a 2046 headset that initiates pairing has no way to surface "show this passkey / confirm this number", and `respondToPairing @15` is the only half of a handshake with no notification that it is needed. Concrete fork: every backend invents its own pairing dialog channel, and a client cannot build one.
- **No GATT value-size or MTU negotiation.** `GattCharacteristic.maxLength @6 :UInt32` exists (462) but nothing negotiates ATT MTU, so a 2046 large-value characteristic (>MTU) has no defined read path.
- **No LE-Audio stream delivery.** `LeAudioConfig` and the Auracast service describe configuration, but `joinBroadcast @3 → AuracastSession` returns a struct with `active @2 :Bool` and `syncHandle @3 :UInt16` and **no audio frames** — the audio must come from audio.capnp, which has no LE-Audio stream path either. The isochronous data path is unmodelled end-to-end.
- **No disconnect recovery contract.** Nothing states whether a broken ACL link auto-reconnects, whether subscriptions survive, or whether in-flight GATT writes are retried — so a 2046 BLE peripheral behind a flaky link behaves per-backend.
- **No BLE address-privacy contract.** `AddressType {public, random, identity, resolving}` (609-615) exists in the filter, but `BluetoothDevice.address` is a single Text with no statement of resolvability, and a rotating IRK address makes the Text address unstable across scans — so `getDevice(address)` may fail for the same physical device. No RPA/IRK concept.
- **`AudioCodecId`/`ClassicAudioCodec` negotiation** (`negotiateAudioCodec @38 → selectedCodec :ClassicAudioCodec`) has no failure variant and no rule for what happens when the device supports none of the offered codecs.

## Zero-cost / eco
- `GattCharacteristic.value @3 :Data` (bluetooth.capnp:456) and `GattEvent.value @3 :Data` (670) are inline GATT values. **Not an R2 violation**: an ATT value is bounded by MTU (~517 bytes), so it is inherently inline and pushing it behind a `T.DataHandle` would add a mapping step for no gain. Reported honestly as "no change needed".
- **`BluetoothDevice` is a 19-field struct returned inside `List(BluetoothDevice)`** by `getPairedDevices @8`, `getConnectedDevices @9` and as `ScanResult.device @0` (381) — paginated, so bounded, but a scan stream ships the full descriptor per advertisement. A scan at 10 Hz for 30 devices copies 10 × 30 × 19 fields/second. A separate lightweight advertisement record (address + rssi + service UUIDs) would remove most of it; `AdvertisementRecord` already exists and is the right shape — so the fix is to not embed the whole device in every `ScanResult`.
- **Idle-power**: a BLE scanner is itself a power consumer, and `ScanFilter.maxAge @5 :T.Duration` (600) exists but no minimum-interval rule for `startScan`, so a client may scan at line rate. `setNotify @27` is a per-characteristic toggle with no batching, so a notifying sensor at 100 Hz produces 100 RPC wakeups/second.
- No `List(Float32)`/pixel/sample bulk payloads in this file — it is a control-plane schema with small inline payloads. R2 is otherwise satisfied.

## UX / implementer guidance
- `class @3 :UInt32` on `BluetoothDevice` (bluetooth.capnp:67) is the 24-bit Class-of-Device with `0 = not available` — a bitfield whose format bits (major/minor/service class) are undocumented, so two backends disagree on what `class = 0x240404` means.
- `BluetoothDevice.manufacturerName/modelName/firmwareRevision/hardwareRevision` (81-87) are `DIS` profile fields exposed on every device, including devices that have no Device Information Service — the backend must invent empty strings.
- `sendFile @29 (address, fileHandle :T.FileId)` — a `T.FileId` from files.capnp is the handle for a file the *client* opened; nothing states who opens it or what happens if it is closed mid-transfer.
- `getMeshNode @41 (address :Text)` and `sendMeshMessage @42 (destination :Text, data :Data, appKeyId :Text)` — mesh addressing by Text string with three different id/kind spellings in one method, while `provisionMeshNode @40 (deviceAddress :T.DeviceAddress, …)` uses the typed address. Four addressing schemes in one file.

## Recommended actions
1. **Fix the address-type schism** (the only wire-breaker): pick one representation. Preferred — add `address :T.DeviceAddress` (or `T.BluetoothAddress`) to `BluetoothDevice` and make the resolver explicit, keeping the Text form as a human-readable `name`-adjacent field. Gain: scan results become usable by every method; removes the single defect that makes the schema unusable. Cost: one field and one documented mapping (backend-issued opaque id ↔ physical address).
2. **Report the `AuracastBroadcast` collision as absent** and leave the ordinals alone. Gain: no wasted work on a defect that does not exist. Cost: none.
3. **Unify UUID representation on `BluetoothUuid`** and define the Text form for the four remaining `List(Text)` sites (or convert them). Gain: filters match records; removes the two-spelling trap. Cost: 4 field type changes and a documented spelling convention.
4. **Make `PairingEvent` reachable** (emit it via a `PairingSubscription` or a `subscribePairing` method). Gain: inbound pairing becomes expressible — otherwise the entire pairing-consent half of Bluetooth is missing. Cost: one method + one subscription.
5. **Replace `BluetoothProfile` and `AudioCodecId` with open tokens** (or delete them in favour of `Text` + `T.MimeType`), keeping `custom` only as a documented escape. Gain: new SIG profiles and new codecs need no ordinal; the enum's own 11-value Audit-7 growth stops being irreversible. Cost: consumers lose `switch (profile)` — which only worked for today's profiles.
6. **Gate `pair`/`unpair`/`writeCharacteristic`/`sendFile`/`provisionMeshNode` behind capability accessors** on a `BluetoothRoot`, leaving `getState`/`startScan`/`getDevice` ungated (discovery stays open per ai.capnp:56-60). Gain: one authority path; a sandboxed app can no longer pair or write GATT. Cost: an accessor layer (~8 methods).
7. **Document units on `BleConnectionParams`** (all fields in 1.25 ms units) or convert to `T.Duration`. Gain: removes a 1000× connection-parameter error. Cost: comments or a type change.
8. **Stop embedding `BluetoothDevice` in every `ScanResult`** (use `AdvertisementRecord` + address + rssi). Gain: removes the dominant copy cost on the scan path. Cost: one field type.
9. Leave `AdvType`, `NdefRecord`-style data, `GattProperties`, `GattWriteType`, `GattKind`, `PairingType`, `AddressType` and the small inline GATT `Data` values alone: each is spec-closed or inherently bounded, and replacing them would add machinery without removing any.
