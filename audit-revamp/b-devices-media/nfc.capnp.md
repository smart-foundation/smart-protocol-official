# audit: `schema/nfc.capnp` (657 lines)

## Verdict
**REWRITE (scope reduction), not a line-fix.** nfc.capnp begins as a competent NFC transport contract — typed `NfcTagId`/`NfcServiceId`, `T.Duration` for ISO-DEP timeouts, a correct `ApduCommand`/`ApduResponse` model that mirrors a real closed standard (ISO 7816), `SecureElement` as a typed routing target, and NdefRecord fields that are faithful to the NFC Forum record format (nfc.capnp:91-96). From line 184 onward it stops being NFC and becomes a **payments + loyalty + transit + EV-charging + identity + Wi-Fi-share + cryptography application stack** bolted onto a radio transport: `PaymentSession{token, amount, currency, approved}`, `LoyaltyProgram{accrueLoyaltyPoints, redeemLoyaltyPoints}`, `TransitSession`, `EvChargingSession`, `DigitalIdentity{passport, driversLicense}`, `AccessControlSession`, `WifiCredentials{ssid, password}`, and `encryptPeerMessage (data, recipientId :Text)`. The Agnostic/Timeless Test fails at litmus #2 (DESIGN_PRINCIPLES.md:110): a consumer does not need a payment-settlement contract to interoperate with an NFC *transport*, and a 2046 contactless payment that uses a different token model must be forced into `PaymentState`. Worse, the file declares its own crypto (`encryptPeerMessage`/`decryptPeerMessage` keyed by a Text recipient, no algorithm field, inline `Data`) where crypto.capnp exists, and carries secrets (`WifiCredentials.password`, `PaymentSession.token`) with no authority gate anywhere. A rewrite that keeps the transport half (tag reading/writing, APDU, HCE, P2P) and deletes the application half is the correct, cheaper-than-maintenance action.

## Wire-breakers
- **No compile errors, no ordinal collisions** (verified mechanically; interface ordinals run @0-@49 with all values distinct).
- `nfc.capnp:483-484` — `registerHceService @8 (service :HceService) -> T.VoidResult` returns no id, while `HceService.name @0 :T.NfcServiceId` (156) is a **UInt64 the caller must invent**, and `unregisterHceService @9 (serviceName)`/`startHce @10 (serviceName)` consume it. So registration is a caller-chosen opaque id with no duplication check, no returned confirmation, and `NfcServiceId` (types.capnp:471) is simultaneously a caller-chosen name and a backend-assigned id. Two 2046 apps registering the same UInt64 silently take over each other's HCE service.
- `nfc.capnp:553-554` — `encryptPeerMessage @38 (data :Data, recipientId :Text) -> (encryptedData :Data)`: ciphertext is returned inline in the result. For a peer message of any size this copies the payload into the request and the ciphertext into the response, and there is no algorithm or parameter field at all, so two backends produce incompatible output with no way to negotiate.

## Duplicates & overlaps
- `WifiCredentials` (nfc.capnp:445-449) vs network.capnp's Wi-Fi credential model and crypto.capnp — the NFC schema owns a Wi-Fi join contract.
- `DigitalIdentity`/`verifyDigitalIdentityAttestation @48` vs crypto.capnp's signature verification, signature.capnp, and auth.capnp — a third attestation model in the batch (location.capnp:287-299 has a fourth).
- `AccessCredentialType` vs bluetooth/biometric/auth.
- `EvChargingSession { stationId, powerKw, duration, cost, currency, connectorType }` vs power.capnp's charging contracts and `WirelessChargingSession` — EV charging inside an NFC transport schema.
- `LoyaltyProgram`/`TransitSession` vs contacts.capnp/vcard.capnp (a loyalty card is a contact's stored credential) and calendar.capnp — application data in a transport schema.
- `NfcTransaction` (290-307) vs device.capnp:226 `getDeviceHistory` and the batch's three other event-log shapes.

## Gaps & holes
- **No authority gating for anything** (see R3) — and this is the one schema in the batch where the missing gate controls physical access and money.
- **No tag-removed / operation-aborted contract.** A 2046 tap is a ~100 ms interaction; `transceive @15` has no timeout parameter of its own (the timeout is a per-tag field on `NfcTag`, nfc.capnp:82) and no cancellation, so a client can be left blocking on a tag that is no longer there.
- **No discovery-scope contract.** `startDiscovery @4 → DiscoverySubscription` (578-581) and `subscribeTags @18 → TagSubscription` (583-586) are **two subscriptions with identical signatures and no stated difference** — does `startDiscovery` power the RF field and `subscribeTags` merely observe? A 2046 client cannot know which to use, and a backend must answer both.
- **No card-emulation conflict semantics**: `setReaderMode @31 (mode :ReaderMode)` (333-343) can put the controller in reader-only or card-emulation-only mode, but nothing states what happens to an already-registered HCE service or an in-flight session.
- **No secure-element access policy**: `listSecureElements @16 → List(SecureElementInfo)` with `paymentReserved @3 :Bool` (573) reports a reservation but nothing enforces it.
- **No NDEF payload bound**: `NdefRecord.payload @3 :Data` (95) has no length check against the tag's `size @3 :UInt32` (71), so a 2046 tag with a large payload is silently unexpressible.

## Zero-cost / eco
- **`encryptPeerMessage @38`/`decryptPeerMessage @46`** copy the entire payload in and the ciphertext out (nfc.capnp:553-554) — the exact pattern `T.DataHandle` exists to prevent, and ai.capnp:74-75 rejects it.
- `SmartPoster.icon @3 :Data` (432) is inline image bytes; small in practice (a smart-poster icon is ~1-2 KB) but unbounded, and `T.DataHandle` is the fix if it ever grows.
- **`NfcTag.ndefRecords @5 :List(NdefRecord)`** is embedded in every `NfcTag` returned by both discovery subscriptions (578-586) and `MultiTag.tags @0 :List(NfcTag)` (455). Discovery therefore ships full NDEF records per advertisement; a 2046 tag with a large payload makes discovery expensive.
- **Idle-power**: `startDiscovery @4` is the single biggest radio-power consumer in this batch, and there is no minimum-interval or duty-cycle contract — a client may leave the RF field on indefinitely. `setReaderMode @31` is the only lever and it is a global mode, not a duty cycle.

## UX / implementer guidance
- **`interface NfcService` and `struct NfcServiceId`** are similarly named but unrelated; `HceService.name` vs `HceService.displayName` vs `HceEvent.serviceName` (600) is three spellings of the service identifier.
- `startPayment @25 (merchantId :Text, amount :Float32, currency :Text)` — `amount :Float32` for **money** and a bare `Text` currency, while `T.FiatAmount` exists (types.capnp:1372-1384, with a `Currency` enum and integer minor units). The same Float32+Text money appears in `PaymentSession.amount/currency` (241-244), `NfcTransaction.amount/currency` (300-302), `EvChargingSession.cost/currency` (193-196), `LoyaltyProgram.points :Int64`, `PrintAccounting`/`PrintCostEstimate` in print.capnp — **at least five sites in this batch**.
- `CheckAccess @28 (doorId :Text) -> AccessControlSession` — a door id as a free string; a 2046 access-control system needs a capability target, not a spelling.
- `AccessControlSession.userId @4 :Text` (276) is a raw Text user id while `T.UserId` exists.
- `BeamEvent.peerAddress @0 :Text` (176) — another address-by-string with no relation to `T.DeviceAddress`.
- `SmartPoster.url @1 :Text` and `CaptureShareRequest`/`media.capnp`'s `shareLink :T.Uri` — this file uses `Text` where `T.Uri` is available.

## Recommended actions
1. **Delete the application half**: `PaymentSession`/`PaymentState`, `LoyaltyProgram`/`LoyaltyPointType`, `TransitSession`/`TransitCardType`, `EvChargingSession`, `WirelessChargingSession`, `DigitalIdentity`/`IdentityDocumentType`, `AccessControlSession`/`AccessCredentialType`, `WifiCredentials`, `SmartPoster`/`SpAction`. Gain: the schema returns to being a transport contract (reread/rewrite tags, APDU, HCE, P2P) that any 2046 payment/loyalty/transit service can build *on top of*; removes ~200 lines of frozen institution-shaped enums and the plaintext-password field. Cost: the application concerns each need a home (a payments schema, a credentials schema) — which is the correct place for them, and they are not implementable in an NFC transport schema anyway.
2. **Delete `encryptPeerMessage`/`decryptPeerMessage`** and delegate to crypto.capnp. Gain: removes an algorithm-free crypto primitive with `Text` key ids and inline bulk copying; one crypto contract instead of two. Cost: P2P encryption is expressed as "send this crypto.capnp output", which is strictly more capable.
3. **Gate the dangerous half**: ungated `getState`/`startDiscovery`/`readNdef`, capability-gated `writeNdef`, `formatNdef`, `makeReadOnly`, `transceive`, `setCardEmulation`, `registerHceService` (ai.capnp:578-584). Gain: a sandboxed app can no longer write arbitrary tags or emulate cards. Cost: an accessor layer.
4. **Distinguish the two discovery subscriptions** or delete `subscribeTags @18`. Gain: removes a duplicated concept with no stated difference (the dual-pattern problem DESIGN_PRINCIPLES.md:255 flags). Cost: one deletion.
5. **Add `T.Error` to `readNdef`, `writeNdef`, `transceive`, `startPayment`, `checkAccess`, `redeemLoyaltyPoints`, `topUpTransit`; add `unknown` to the event shapes.** Gain: a tag-removed-mid-read becomes reportable, and a failed loyalty redemption becomes diagnosable. Cost: result structs.
6. **Replace money with `T.FiatAmount` everywhere** (and `userId :Text` with `T.UserId`, `url :Text` with `T.Uri`). Gain: no floating-point currency bugs; one money representation across the batch. Cost: type changes at 5+ sites.
7. **Return the `NfcServiceId` from `registerHceService`** so the caller does not invent an opaque id. Gain: removes the self-collision hazard. Cost: one result field.
