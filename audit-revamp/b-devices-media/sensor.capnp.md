# audit: `schema/sensor.capnp` (454 lines)

## Verdict
**FIX (targeted) — and this is the schema where the "device classes that do not exist yet must be expressible today" requirement fails most visibly.** The core mechanics are right (typed `T.SensorId`, `cancel` on subscriptions, a `batchCount` framing convention, `axisLabels`/`units`/`maxBatchSize` as open per-sensor descriptors — sensor.capnp:92-100 — and `SamplingRateConfig.hz :T.Frequency` at sensor.capnp:232 being exactly the right fix for fractional rates). But `SensorType` is a **44-value enum** whose own audit trail proves it is closed by release schedules rather than mathematics: Audit-7 added 14 values in one revision (sensor.capnp:54-68). A 2046 bioimpedance or quantum-magnetometer sensor has nowhere to go but `custom @43`, a bare ordinal with no semantics — so `getSensorsByType(type)` cannot express it and every app that switches on `SensorType` must be patched. Compounding that, **six Audit-7/8 data types are unreachable** (`SpatialSensor`, `GestureSensor`, `SpectrometerData`, `GasSensorData`, `RadiationSensorData`, `ContextSnapshot` — no method returns them), the batch subscription API is `pull(pagination)` — pagination offsetting into a live stream, which silently drops readings — and `permissionCapability @16 :Text` puts a capability *name* in a discovery struct.

## Wire-breakers
- **No compile errors, no ordinal collisions** (verified mechanically).
- `sensor.capnp:238, 242` — `SensorSubscription.pull @0 (pagination :T.Pagination) -> (readings :List(SensorReading), total :UInt32)` and `BatchSubscription.pull @0 (pagination :T.Pagination)`. `T.Pagination` is `{offset, limit}` (types.capnp:248-251) — an offset into a **stable list**. A live sensor stream has no stable list, so `pull(offset=5, limit=10)` has no defined meaning: a backend may skip the first 5 readings (losing them) or return 10 from the newest. This is a wire-level ambiguity introduced by a well-intentioned "Rule 9 bounded results" fix, and it silently destroys data on the batch path, where `batchCount` concatanation already makes the framing subtle (sensor.capnp:125-127).
- `sensor.capnp:174` — `pull @4 (subscription :SensorSubscription) -> (readings :List(SensorReading))` on the service, in addition to `SensorSubscription.pull`. Two pull paths, no statement that they read the same queue; a client that mixes them can duplicate or lose readings.

## Duplicates & overlaps
- `GnssFix` (sensor.capnp:257-270) vs location.capnp `LocationData` — the clearest cross-schema duplicate in this batch (same physical quantity, different field names, one with `hdop`/`vdop` the other without).
- `BiometricSensorType` vs input.capnp `BiometricModality` vs biometric.capnp.
- `SensorCalibration` (sensor.capnp:306-315) vs display.capnp `CalibrationStatus` (a struct, 690-695) vs camera.capnp `CalibrationStatus` (an enum, 418-424) — three calibration shapes, none shared.
- `SensorAccuracy` vs location.capnp `LocationAccuracy` (both 5-bucket ladders with different names).
- `SpectrometerData`/`AirQualityIndex`/`GasSensorData`/`RadiationSensorData` are per-class result types with no shared envelope — every future sensor class would add another one.

## Gaps & holes
- **`getGnssFix @11`, `getAirQuality @12`, `getFallDetection @13` are global, id-less singletons.** `getGnssFix()` — which GNSS sensor? A 2046 device with two receivers (internal + external) returns ambiguous data, and `getFallDetection()` — which wearable? There is no sensorId parameter and no enumeration of which sensors feed them. Demonstrated fork: backends invent a "the GNSS" convention.
- **Hotplug/removal semantics for subscriptions.** Nothing states what happens to readings in flight when a sensor is unplugged, whether `pull` returns them first, or whether the subscription ends. Same gap as device.capnp, but here the data is a real-time stream, so loss is immediate.
- **Overflow semantics** (what happens when the producer outruns the consumer) — undefined for all three subscriptions (see R7).
- **No timestamp source.** `SensorReading.timestamp @1 :T.Timestamp` (wall clock) but nothing states whether it is the sensor's sample time or the delivery time. For a batched reading, `batchCount > 1` concatenates values whose timestamps are not individually recorded (sensor.capnp:125-127), so the timing of all but the last sample is unrecoverable. `T.MonotonicTimestamp` exists (types.capnp:111) for exactly this.
- **`calibrate @15 (sensorId) → T.VoidResult`** gives no way to compute calibration (`SensorCalibration.offset`/`scale` are reported but never set), no progress, and no error. Calibration is named in the audit brief as a contract gap; here it is a button with no input and no output.
- **`setFusionConfig @17 (config :SensorFusionConfig)`** sets fusion globally, with `sensors :List(T.SensorId)` inside the config — a client can add sensors it does not own. `SpatialSensor`, `GestureSensor`, and `ContextSnapshot` remain unreachable.
- **Power/batching**: `maxBatchSize @14 :UInt16` and `latencyHint @19 :T.Duration` exist (good — batching is the eco win for sensors), but nothing states the *minimum* delivery latency trade-off or whether a wake-up sensor batches at all (`wakeUp @10 :Bool`).

## Zero-cost / eco
- **`SensorReading.values @2 :List(Float32)`** (sensor.capnp:123) is copied per reading. For a 3-axis accelerometer this is 12 bytes and *not* a meaningful copy cost — flagging it as R2 would be noise. The honest reading is that the **interpretation gap** (no unit/axis binding, no length check) is the real defect, not the copy.
- **`SpectrometerData.spectralData @2 :List(Float32)`** (sensor.capnp:375) is the genuine bulk case: a spectrometer produces hundreds to thousands of bins per reading (2048 channels × 4 bytes = 8 KB), at up to 100 Hz = **800 KB/s copied inline** — and the type is unreachable, so today that data arrives as an untyped `values` list instead. Fix: `spectralData :T.DataHandle`.
- **`ContextSnapshot.readings :1 :List(SensorReading)`** (sensor.capnp:366) — an unbounded inline list of readings (unreachable today; if wired up it would copy a whole batch snapshot per call).
- **Batching is implemented but unenforced**: the `batchCount` framing means a consumer that pulls rarely receives one large inline `values` array (100 accelerometer readings = 300 floats = 1.2 KB), so a slow consumer gets bigger and bigger copies. `maxBatchSize` bounds server-side memory but the client-side copy grows with the poll interval.
- **Idle-power:** the three `get*` singletons (`getGnssFix`, `getAirQuality`, `getFallDetection`) are polling-only with no subscription, so a location or air-quality widget must poll continuously — and each call may wake the GNSS radio, the single most power-hungry sensor on the device. A pull-based subscription (already the schema's own pattern) or a `minInterval` on the getter removes it.

## UX & implementer guidance
- Four ways to express a sampling rate: `subscribe @2 (rate :SamplingRate)`, `subscribeCustom @3 (rateHz :UInt32)`, `subscribeBatch @8 (requests :List(SubscribeRequest))` where `SubscribeRequest.rateHz @1 :UInt32` is marked DEPRECATED and `rate @2 :SamplingRateConfig` is preferred, and `SamplingRateConfig` itself. A 2026 client must choose among four spellings for one quantity.
- `triggerData @15 :Text` (sensor.capnp:102) — "For wake-up sensors: what triggered the wake" is a free-text field with no vocabulary.
- `powerMa @9 :Float32` (sensor.capnp:89) — milliamps in the field name, where `T.Current` (types.capnp:506) exists.
- `version @4 :T.Version` on `SensorInfo` is a *sensor hardware* version, while `T.Version` is used for schema/ABI versioning everywhere else — two meanings of one type.
- `getSensorsByType @7` returns `List(SensorHandle)` (id + name only) while `listSensors @0` returns full `SensorInfo` — a client must call twice to filter by type and read capabilities.

## Recommended actions
1. **Replace `SensorType` with an open token + keep `units`/`axisLabels` as the machine-readable part.** Concretely: `type @0 :Text` (an open class token, unknown values ignored per ai.capnp:43-47) and, for the clients that need structure, `quantity`/`unit` fields. Gain: a 2046 sensor class is expressible today with no schema change; `getSensorsByType` becomes a Text filter that needs no ordinal. Cost: a type change plus a documented convention for tokens — but this is precisely the change the doctrine demands, and the enum's own growth (14 values in one revision) is the evidence.
2. **Bind interpretations to readings**: add `unit :Text` (or `T.MimeType`-style) and a declared axis count/semantics to `SensorReading`, and record per-sample timestamps in batches. Gain: a reading becomes self-describing and type-checkable on the wire; removes the cross-call coupling to `SensorInfo`. Cost: 2 fields per reading (a real but bounded cost on a hot path — an alternative is a `sensorDescriptorId` on the reading, which is cheaper still).
3. **Fix `pull` to a max-count** (`pull (maxCount :UInt32)`) and delete the offset semantics; add `T.SubscriptionResult`-style `ended`/`error`. Gain: stops silently dropping readings and makes end-of-stream honest. Cost: one signature change.
4. **Wire up the six orphan data types or delete them.** Gain: either the lidar/spectrometer/gas/radiation contracts work, or the schema stops promising features it does not deliver. Cost: 6 parameters (preferred) or 6 deletions.
5. **Add the missing sensorId to the singletons** (`getGnssFix (sensorId)`, `getAirQuality (sensorId)`, `getFallDetection (sensorId)`) or convert them to subscriptions. Gain: two-GNSS and two-wearable devices stop being ambiguous; removes continuous polling (a GNSS wakeup per poll is a direct battery cost). Cost: one parameter each, plus a `SensorSubscription`-shaped stream.
6. **Replace `permissionCapability :Text` with a capability accessor**: ungated `listSensors`/`getInfo` (discovery is open, per ai.capnp:56-60), and a `stream (authority :Capability, sensorId, rate) → SensorSubscription` accessor. Gain: one authority path; removes the dead-end string. Cost: an accessor layer on `subscribe`/`subscribeCustom`/`subscribeBatch`.
7. **Fix `SensorEvent.data :T.Meta` → `T.StringMap`.** Gain: an event can carry more than one key/value. Cost: one field type.
8. Leave `SensorAccuracy`, `SamplingRate`, `maxBatchSize`/`latencyHint` alone: the accuracy ladder has a `custom` escape and the batching machinery is genuinely good eco design; changing them costs more than it buys.
