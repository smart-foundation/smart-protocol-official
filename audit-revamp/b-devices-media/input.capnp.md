# audit: `schema/input.capnp` (743 lines)

## Verdict
**FIX (targeted).** input.capnp has a sound core — typed ids everywhere (`T.DeviceId`, `T.KeyboardLayoutId`, `T.SeatId`, `T.KeyCode` per Audit-3/5), pagination on every list, `cancel` on every subscription, `backendSpecific :T.StringMap` replacing the `sysPath` Linux noun (input.capnp:160-161) — and its Audit-7 extended-modality block (eye tracking, BCI, spatial, digital crown, cabin attention) is a genuinely good 2046 bet, because a brain-computer interface and a cabin-attention sensor are expressible today. Three things need fixing. (1) **`T.KeyCode.code :UInt32` has no defined value space** (types.capnp:928-930), so `emulateKey` requires a vocabulary the protocol never publishes — the batch's worst implementer trap. (2) **The schema has no key or pointer event path at all**: `subscribeInputEvents @46` carries eye-tracking/brain/spatial/crown/cabin events only, and `DeviceEvent` is device *lifecycle*, not input. The hottest input path has no contract. (3) Three parallel taxonomies for device capability (`DeviceKind`, `InputCapability`, plus `DeviceFilter.requireCapabilities :List(Text)`) and three for gestures (`GestureKind` 25 values, `T.TouchGesture`, display.capnp's `GestureType`).

## Wire-breakers
- **No compile errors, no ordinal collisions** (verified mechanically).
- `types.capnp:928-930` — `struct KeyCode { code @0 :UInt32; }` with comment "Cross-platform semantic key code". **The code space is undefined.** A client calling `emulateKey @27` (input.capnp:59) cannot know whether `code=30` means Linux `KEY_A`, ASCII `'A'`=0x41, or HID usage 0x04. This is not a compile error; it is the single largest source of divergent implementations in the file, and it also silently breaks `KeyTrigger.key` (input.capnp:315) and every key binding.
- `getDeviceCoordination @58 (deviceIds :List(T.DeviceId)) -> (coordination :DeviceCoordination)` (input.capnp:106) takes a list of N devices and returns **one** `DeviceCoordination`. For two devices with different coordination configurations there is no representation; and since `mode`/`syncTolerance`/`syncHaptics` are inside the returned struct, the caller cannot tell which device the single result describes.

## Duplicates & overlaps
- `GestureKind` ≡ `T.TouchGesture` ≡ display.capnp `GestureType` (three gesture vocabularies in the batch).
- `BiometricModality` ≡ sensor.capnp `BiometricSensorType` (and biometric.capnp owns the domain).
- `DeviceKind` ≡ `InputCapability` (same file).
- `HapticWaveform.amplitudeEnvelope :List(Float32)` and `amplitudePoints :List(AmplitudePoint)` (input.capnp:281, 287) — two representations of a haptic waveform, with the comment "Use instead of amplitudeEnvelope when precise timing is needed". Two ways to express one curve, one of which cannot express timing.
- `GamepadState.touchpad :TouchpadState` (input.capnp:242) embeds `points :List(TouchPoint)` — the touch path duplicated inside the gamepad path.
- `IntentReference` (input.capnp:334-339) duplicates intent.capnp's intent model with `mimeType :Text` instead of `T.MimeType`.
- `TouchpadState`/`TouchPoint` (input.capnp:247-262) vs display.capnp's `StylusDisplayEvent` (566-573) vs console.capnp's `StylusInputEvent` (258-269) — three stylus representations in three schemas.

## Gaps & holes
- **No key or pointer event contract.** `subscribeInputEvents @46 (filter :DeviceFilter) → InputEventSubscription` (input.capnp:88-89) delivers only the five Audit-7 extended modalities. `DeviceSubscription.pull → List(DeviceEvent)` (input.capnp:40) is device lifecycle. There is no way to subscribe to a keypress, a mouse motion, or a touch contact. This is the batch's most consequential hole: DESIGN_PRINCIPLES.md:454 asserts "X11 → Wayland → custom compositor ✅ Yes … compositor.capnp defines surfaces, commits, **input events**", and that claim is false for the input half — a compositor cannot implement itself against this schema. Every implementer will invent the key path (libinput, an evdev node, a Wayland protocol), which is precisely the fork the protocol exists to prevent.
- **Subscription overflow semantics undefined.** Nothing states what happens when a producer enqueues faster than the consumer pulls (drop-newest? drop-oldest? grow unboundedly?). Every subscription in the file is affected; a missed modifier or held-key event desynchronises a client permanently.
- **`getIdleTimeout @9`/`setIdleTimeout @10`** define idle on the Input service, while session.capnp:40-41,52 defines `idleTime`/`setIdleTimeout`/`getIdleState` and screenlock.capnp:72-75 defines `getIdleTime`/`setIdlePolicy`. Three idle contracts (see screenlock audit).
- **`emulateSequence @28 (text :Text)`** has no defined encoding for text that cannot be typed (characters outside the layout, RTL, combining marks) and no result.
- **`getEyeTrackerInfo @40` and friends are per-device getters with no calibration path** — eye-tracking without a calibration contract is unusable, and `calibration :Bool` (input.capnp:441) only advertises support.
- **`playRumble @20`/`engageHaptic @22`** return no error when a device has no actuator, and `stopHaptic @23 (deviceId, instanceId :UInt64)` takes a raw UInt64 handle while `engageHaptic` returns `UInt64` — an untyped handle pair.

## Zero-cost / eco
- **`GamepadState.values :List(Float32)`, `buttonsBool :List(Bool)`, `hats :List(Int32)`** (input.capnp:234-238) are inline lists on the 60-250 Hz polling path. The file's own header claims "Zero-cost: inline structs, no heap" (input.capnp:426) — which is the inverse of the truth for a *message*: inline list contents are copied into the message on every pull. Concrete cost: an 18-button/8-axis/2-hat controller = 28 values copied per pull per device; at 250 Hz that is ~7,000 copied values and ~28 message allocations per second per controller, plus a fresh copy for each.
- **`subscribeGamepads @18 → pull → List(GamepadState)`** returns the **entire gamepad fleet** per pull, including each device's `name` and full `TouchpadState`. Four controllers polling at 4 ms ship four complete states per frame. A per-device delta frame, or a shared snapshot buffer, removes the whole copy.
- `emulateSequence @28 (text :Text)` — unbounded inline text; a 100 KB paste is copied whole.
- **Idle-power:** `subscribeModifiers @6`, `subscribeIdle @11`, and the gamepad poll loop each keep an independent wakeup stream, and none has a coalescing or minimum-interval rule.
- `HapticWaveform.amplitudeEnvelope :List(Float32)` (input.capnp:281) — a precise waveform can be thousands of samples copied into a message for a vibration that a driver can hold as a shared buffer.

## UX & implementer guidance
- `DeviceEvent.battery @3 :BatteryChange` carries `previousPercent`/`currentPercent :UInt16` (input.capnp:221-225) — the only event in the protocol that ships *two* samples, forcing clients to handle both.
- `registerKeyBinding @24 → (id :T.KeyBindingId)` while the binding's scope is `BindingScope { surfaceId, applicationId, seatId }` with "Empty = global/system binding" (input.capnp:342-343) — an all-zero struct is the global scope, which collides with a binding scoped to surface 0.
- `listBiometricsTemplates @32`/`enrollBiometric @33`/`removeBiometric @34` re-enter a domain owned by biometric.capnp (per the file's own comment at line 348); `BiometricTemplate.useCount` is trivially forgeable telemetry.
- `CabinAttentionEvent.subject @1 :Text` documented as `"driver", "passenger-1", "child-rear"` (input.capnp:623-626) — free-text subject ids with no registry; a backend counting passengers cannot name passenger-7 without inventing a spelling.
- `SpatialTrackingType {insideOut, outsideIn, hybrid}` (input.capnp:539-544) documents `insideOut` as "(Quest, Vision Pro)" — vendor product names in a distinguishing example, encouraging backends to classify by product rather than architecture.

## Recommended actions
1. **Add the missing key/pointer/touch event contract** (a union of `KeyEvent`, `MotionEvent`, `TouchEvent` carried by `InputEventSubscription`, or a distinct subscription). Gain: closes the batch's biggest hole; makes the compositor swap test the doctrine cites actually pass; removes the per-backend key path. Cost: ~20 lines and an ordinal addition — the highest-value single change in this file.
2. **Publish the `T.KeyCode` domain** — either a named token (`Text`) or a fixed table (Unicode codepoint, or USB-HID usage ids as an explicit conformance section). Gain: makes `emulateKey`, `KeyTrigger`, and every binding implementable without guessing. Cost: a decision, documented in the schema header; an enum here would be the wrong fix (R1), so publish the mapping, don't freeze it.
3. **Collapse the three capability taxonomies into one** — keep `DeviceKind` for *what the device is*, replace `InputCapability` with the same list, and delete `requireCapabilities :List(Text)` or make it an escape hatch only. Gain: one classification, one filter. Cost: one field deprecated.
4. **Replace `GestureKind` with a parameterised gesture** (`GestureDef.touches` + a direction/kind token) or delegate to `T.TouchGesture`. Gain: removes a 25-value frozen list and makes `startGestureLearning` able to learn new kinds. Cost: a real redesign of 10 ordinals — do it now, pre-release.
5. **Add `unknown @N :UnknownEvent` to `DeviceEvent` and `T.SubscriptionResult`-style error/ended to all six subscriptions.** Gain: forward-compatible events and honest end-of-stream. Cost: two structural edits.
6. **Unify the battery scale** on `power.capnp`'s `BatteryState` (or an explicit `T.BatteryLevel` with a `Bool present`), replacing `0xFFFF`, `-1.0`, and three different scales. Gain: one battery contract across input/device/power. Cost: a shared type + three call sites.
7. **Move gamepad frames to a shared snapshot buffer** (or at minimum a per-device pull with a max-count) and delete `GamepadState.name` from the frame. Gain: removes the ~7,000 copies/second/controller cost. Cost: a driver-side buffer contract.
8. **Move `KeyAction.runCommand` behind a capability accessor** (ai.capnp:578-584 pattern) or delete it in favour of `invokeIntent`. Gain: removes unattended command execution from a bindable action. Cost: one variant + an accessor.
