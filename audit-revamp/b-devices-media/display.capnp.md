# audit: `schema/display.capnp` (897 lines)

## Verdict
**FIX (targeted).** display.capnp is the best-structured large schema in this batch: real typed ids throughout, `cancel` on every subscription, `T.Pagination` via `MonitorFilter`, per-feature forward-compat variants, an explicit unit comment on night-light temperature (display.capnp:93), and `IccProfile.data`/`getIccProfileData` correctly using `T.DataHandle` for multi-KB profiles (display.capnp:539, 193). The header's claim of "zero-backend-assumption … No Wayland, X11, DRM/KMS" (display.capnp:7-9) is *almost* true. The problems are concentrated and repairable: three parallel vocabularies for colour space, three for refresh rate, two for DPMS, two for gestures, an unbounded `getMonitors` that ships each monitor's full mode list twice, one method (`writeConsoleText @85`) that reaches into console.capnp's domain and returns `()` with no error, and an Audit-7/9 feature sweep (signage, kiosk, tiling, multi-user displays, wireless display pairing, gesture zones, colour-accuracy testing, recommendations) that is application policy rather than display contract. Targeted fix.

## Wire-breakers
- **No compile errors, no ordinal collisions** (verified mechanically).
- `display.capnp:243` **`writeConsoleText @85 (text :Text) -> ();`** — an empty result list. Not a syntax error, but it silently discards every failure of a write to a terminal, which is a real failure mode (a blocked/overflowing console). DESIGN_PRINCIPLES.md:428 ("NEVER swallow errors silently") and :418 ("Methods that always succeed return `Void`") both point at this. It is also the only method in the 19 assigned schemas that returns `()` rather than `Void`/`T.VoidResult`.
- `display.capnp:873` — `ModeSpec.flags @5 :UInt32` documented as "Bit flags bitwise-ORed from **`DisplayModeFlags`**". **`DisplayModeFlags` is defined nowhere in the schema set** (verified by grep: the only occurrence in the repo is this comment). An implementer is instructed to OR bits from a nonexistent type; each backend will invent its own bit values, and a mode's flags are unreadable across backends.

## Duplicates & overlaps
- Within the batch: `WatermarkRequest`/`WatermarkPosition` (display.capnp — *not present*; they are duplicated camera.capnp:291-305 ≡ capture.capnp:291-305), `CalibrationStatus` as a **struct here** (display.capnp:690-695) vs the **same-named enum** in camera.capnp:418-424 — same identifier, different kind, different fields, so any consumer importing both gets a name clash and a semantic fork. `NightLightGeoConfig.latitude/longitude` (703-707) and `NightLightSchedule.location :T.Vec2` (660) are two geolocation encodings in one file, and a third/fourth against `T.GeoCoordinate` (types.capnp:1441) and camera.capnp:494-496.
- Cross-batch: `DpmsState` ≡ framebuffer.capnp:558; `ColorSpace` ≡ `T.ColorSpace` ≡ `FramebufferColorSpace`; `GestureType` ≡ `T.TouchGesture` ≡ input.capnp `GestureKind`; `StylusDisplayEvent` (display.capnp:566-573) overlaps input.capnp's `TouchPoint`/stylus and console.capnp's `StylusInputEvent`.
- `writeConsoleText @85` (display.capnp:243) duplicates console.capnp:359 `writeText @2` — two write paths for the same terminal, one of which cannot report failure.

## Gaps & holes
- **No transaction/ownership model for `testChanges`/`applyChanges`.** Both take only an `outputId` (display.capnp:110-111); the "changes" are whatever previous `setMode`/`setBrightness`/`setRotation` calls left in server-side state. With two clients (a settings app and a game) the pending configuration is shared mutable state with no owner, no lease, and no way to read back what is pending. Every backend will invent its own semantics, and the two clients will race. High fork risk.
- **No coordinate-space or range declaration.** `setFocus`-style `x/y` do not exist here, but `GestureZone.x/y/width/height` (display.capnp:789-792) is documented "normalized 0.0–1.0" while `DisplayUserSession.viewportX/Y/Width/Height` (773-776) is *also* "normalized 0.0–1.0" without saying normalized to what (the output? the logical layout?). `setScale @13 (scale :Float32)` has no documented range at all.
- **`negotiateContentProtection @65`** can fail (the display refuses HDCP) — the failure arrives in a `ContentProtectionResult` whose `error` is `T.Error` (good), but nothing states whether a failed negotiation invalidates the mode, so a client cannot tell whether it may still present.
- **`HdcpState.version @1 :UInt8`** is documented as "12 = 1.2, 22 = 2.2" — a magic-number encoding with no type, duplicating `ContentProtectionLevel {hdcp14, hdcp22, hdcp30}` (display.capnp:681-688) which encodes the same information a third way.
- **`AdaptiveSyncCaps.variant @1 :UInt8`** ("backend-decided encoding") is unreadable, while the adjacent comment names two variants it cannot express: "Adaptive sync (FreeSync/G-Sync) supported" (display.capnp:293). An implementer trap written into the struct's own doc.

## Zero-cost / eco
- **`getMonitors @0` / `listMonitorsFiltered @71` ship `Monitor.modes` (a `List(DisplayMode)`) plus `Monitor.currentMode`** — i.e. every call re-ships the active mode as a second copy of an element already in `modes` (display.capnp:286 vs :288). 4 monitors × 40 modes = 160 `DisplayMode` structs copied per call, of which 4 are duplicates. `DisplayMode` carries 8 fields including a `T.Vec2`. Fix: return mode ids, or paginate `modes`.
- `writeConsoleText @85 (text :Text)` accepts unbounded text; a client forwarding a large log ships it whole (see console.capnp's `writeText`).
- `runColorAccuracyTest @84` and `getDisplayRecommendation @68` are both on-demand computations with no rate limit; nothing prevents a client from calling them per frame.
- **Idle-power:** `subscribeBrightness @6`, `subscribeRefreshRate @24`, `subscribeHdr @31`, `subscribePowerBudget @54` are four independent per-output subscriptions with no coalescing rule; an ambient-light-driven brightness loop can wake the client at display rate.

## UX & implementer guidance
- `setMode @11 (outputId, mode :T.DisplayModeId)` takes a typed id, but `DisplayProvider.setMode @3 (modeId :Text)` (display.capnp:847) and `ModeSpec.modeId :Text` take strings — a fourth mode-id representation.
- `DisplayProvider` (display.capnp:839-854) is **returned by no method anywhere in the protocol** (verified by grep). Its whole subtree — `ConnectionSubscription`, `ConnectionEvent`, `ModeSpec`, `DisplayMetadata`, `ConnectionStatus` — is unreachable, so five types and one interface are dead contract.
- `Orientation` (display.capnp:221-226) lives in print.capnp as `Orientation {portrait, landscape, auto}` and in display.capnp only as `T.SurfaceTransform` — two spellings of the same setting in one file.
- `PrintColorSpace` in print.capnp is yet another colour-space enum; a client setting a printer profile from a monitor profile must map through three enums.
- `DisplayFilter` has only three fields (`connection`, `enabled`, `hdrCapable`) while `Monitor` has 27 — the filter cannot select on any of the Audit-7 properties it must therefore ship.

## Recommended actions
1. **Delete the local `ColorSpace`, `DpmsState` and `GestureType`; use `T.ColorSpace`, `T.PowerSleepState`, `T.TouchGesture`.** Gain: removes three duplicate vocabularies (and one verbatim pair with framebuffer.capnp) and lets ICC profiles, monitors and compositors share one colour language. Cost: three type-reference changes; pre-release, ordinal-neutral for consumers.
2. **Merge the refresh-rate setters into one `T.Frequency`-typed method and deprecate `setRefreshRate @23`.** Gain: fractional/VRR rates expressible on the canonical path; removes the "UInt32/Float32 inconsistency" the header already apologises for. Cost: one ordinal deprecated, one added. Same for `DisplayMode.refreshRatex100` → `T.Frequency`.
3. **Fix `writeConsoleText @85` → `-> T.VoidResult` or delete it** (console.capnp owns terminal writes). Gain: honest errors, one write path. Cost: one signature change or a deletion.
4. **Define `DisplayModeFlags` or replace `ModeSpec.flags` with a typed list** (mirroring framebuffer.capnp:191 `flags :List(DisplayFlag)`). Gain: removes the dangling-reference trap. Cost: one type or one field.
5. **Add `unknown @N :UnknownEvent` to `MonitorEvent` and replace `ApplyResult`/`FieldError` with a `T.Error`-carrying result.** Gain: forward-compatible events and retryable failures, both per doctrine. Cost: two structural edits.
6. **Give `testChanges`/`applyChanges` an explicit pending-configuration parameter (or a lease).** Gain: removes the shared-mutable-state fork between concurrent clients. Cost: one request struct — the highest-value single fix in this file.
7. **Cut the non-display policy blocks**: `KioskConfig.allowedApps`, `DisplayUserSession`, `GestureZone`, `setSignageConfig`, `getDisplayRecommendation`. Gain: removes permission strings and app policy from a display contract; shrinks the surface that must be versioned forever. Cost: those concerns belong to shell/session/settings and must move there.
8. **Paginate `getMonitors` and stop shipping `currentMode`.** Gain: bounded enumeration, one copy of the mode list. Cost: one `T.Pagination` param, one field deletion.
