# audit: `schema/power.capnp` (489 lines)

## Verdict
**KEEP with targeted fixes — the best schema in this batch.** power.capnp is what the rest of the device/Media schemas should look like: every physical quantity is wrapped in a unit-bearing struct (`T.TemperatureKelvin` in Kelvin, `T.Voltage`, `T.Current`, `T.Duration` — power.capnp:97-101, 187), the header documents the unit conventions, ids are typed (`T.PowerProfileId`), `T.Pagination` is on list operations, `cancel` is on both subscriptions, and there are no inline bulk payloads at all. There are no wire-breakers and no ordinal collisions. The defects are narrow and worth fixing but do not justify a rewrite: `ThermalState` (power.capnp:171-177) is a **verbatim duplicate of device.capnp:368-374**; three overlapping state vocabularies (`PowerState`, `SleepState`, `PowerMode`-in-device, `T.PowerSleepState`, `ConsolePowerMode` — five system-wide); `PoEInfo.lldpMedPolicy @3 :Text` puts an LLDP-MED (a named networking protocol) in a required field; `PoEClass` bakes IEEE 802.3 wattages into enum variants; `suspend`/`hibernate`/`reboot`/`shutdown @4-7` are ungated, so any client can power off the system while the protocol has an `InhibitHandle` concept it does not consult; and three types (`IgnitionState`, `SleepState`, `SolarInfo`) are referenced by no method.

## Verdict detail
Why KEEP rather than FIX: every finding below is either a duplicate whose fix is a type-reference change (3 of them), a missing gate (1), or a dead declaration (3). Nothing in this file leaks implementation the way audio.capnp's transport enum or nfc.capnp's payment stack does, and nothing forces a copy. The doctrine's own verdict table does not even list power.capnp under "needs fixes", and on this evidence that is correct.

## Wire-breakers
- **None.** No compile errors, no ordinal collisions, no undefined references (verified mechanically and by grep).
- `power.capnp:589` — the file ends mid-declaration at line 489 with `timestamp @8 :T.Timestamp;` and a closing brace, and `ThermalRunawayPrediction` is complete. No truncation.

## Duplicates & overlaps
- `ThermalState` ≡ device.capnp:368 (verbatim).
- `UsbPdContract`/`negotiateUsbPd` vs usb.capnp's `UsbPowerDelivery`/`initiatePdNegotiation`.
- `WirelessChargingConfig` vs nfc.capnp's `WirelessChargingSession`.
- `PowerBudget {maxPowerWatts, thermalLimitWatts, currentDrawWatts, headroomWatts, subsystems}` (power.capnp:222-233) vs usb.capnp:344-355 `UsbPowerBudget` vs display.capnp:624-629 `DisplayPowerBudget` vs device.capnp:449 `maxPowerWatts` — four power-budget shapes.
- `SolarInfo` vs `GridEnergyInfo.solarProduction`.
- `ThermalRunawayPrediction` (power.capnp:471-489) vs device.capnp:368 `ThermalState` vs audio.capnp:1198 `temperature :Int32` (millidegrees, a fourth temperature unit in the batch) — thermal state reported three ways.
- `getPowerBudget @9`/`setPowerBudget @10` vs device.capnp's `DevicePolicy.maxPowerWatts` (449) — two places to bound power.

## Gaps & holes
- **No inhibitor contract for suspend/shutdown.** `T.InhibitHandle` exists (types.capnp:17) and screenlock.capnp:74 uses it for idle; power.capnp's lifecycle methods have no way to register an inhibitor or to be told that shutdown is imminent. Concrete fork: every backend answers differently whether a `shutdown()` while an inhibitor is held fails, defers, or ignores the inhibitor. High-stakes (data loss), cheap to fix.
- **No "power state will change" event.** There is no subscription for suspend/resume (only battery and telemetry), so a client cannot flush state before suspension; the only warning is the shutdown call itself.
- **No per-device power attribution for the sources power.capnp claims.** `TelemetryConfig.subsystems @2 :List(Text)` (power.capnp:212) is an open list with no registry of subsystem names, so two backends report `{"gpu"}` and `{"GPU"}` as different subsystems.
- **No battery-aging or cycle-limit contract**: `BatteryState.cycleCount`/`soh` (105-107) are reported but no method or event reacts to a degraded battery.
- **`configureCellBalancing @18 → T.VoidResult`** with no way to observe the effect other than `getCellBalancingStatus @19` (polling), and `CellBalancingStatus.balancingCells @2 :List(UInt32)` (428) indexes cells with no declared cell-numbering convention.
- **No thermal-limit event**: `getCellBalancingStatus`, `predictThermalRunaway` and `DeviceHealth`-style checks are all polled; nothing pushes a "throttle imminent" notice.

## Zero-cost / eco
- **No inline bulk payloads anywhere** — no `List(Float32)`, no unbounded `Data`, no pixel/sample buffers. Correct.
- **Polling-forcing pattern (the file's one eco issue):** `getChargingInfo @11`, `getGridEnergy @15`, `getCarbonIntensity @16`, `getPoEInfo @17`, `getFuelGauge @20`, `getCellBalancingStatus @19`, `predictThermalRunaway @21`, `getConsumableStatus`-equivalents are all snapshot getters with **no subscriptions and no change events**. A UI showing charging state, battery level, or thermal risk must poll. `getCarbonIntensity (region)` is the worst: a carbon-aware scheduling widget polls a *network* query, waking the radio for data that changes hourly. The file already has the fix in its own vocabulary — `subscribePowerTelemetry @8 (config :TelemetryConfig)` with `interval` (power.capnp:40, 208) — so the remedy is to extend telemetry to these sources or add `T.SubscriptionResult`-shaped subscriptions.
- **`BatterySubscription` has no coalescing:** it delivers on every change, so a 1 %-granularity battery stream wakes the client hundreds of times per charge cycle. A documented "producer MAY coalesce within `interval`" (or a threshold parameter) removes it without new machinery.
- `PowerSample` (194-202) is small and correct; `TelemetryConfig.interval` is good eco design and the only rate control in the batch's device schemas.

## UX / implementer guidance
- `power.capnp:51` — `negotiateUsbPd @12 (requestedVoltage :T.Voltage, requestedCurrent :T.Current) -> (contract :UsbPdContract)`: negotiation *requests* a voltage/current but there is no enumeration of what the source can actually offer (that lives in usb.capnp's `availablePdos`), so a client must guess at a valid request.
- `BatteryState.percentage @1 :UInt32` (0-100) vs device.capnp's `batteryLevel :Float32` (0.0-1.0, `-1.0` = unknown) vs input.capnp's `batteryPercent :UInt16` (0-100, `0xFFFF` = unknown) — three scales, two sentinels, one concept. A 2046 client must special-case every battery field it reads.
- `ChargingInfo.tempLimit @6 :TemperatureKelvin` and `ThermalRunawayPrediction.currentTemperature @3` are Kelvin (correct), while audio.capnp:1198 uses millidegrees Celsius and display.capnp:712 uses Celsius. Four temperature units in the batch.
- `getCarbonIntensity @16 (region :Text)` — a free-text region key with no registry; two backends will not agree on what `"EU-DE"` means.
- `PowerProfile` is only `{id, name, description, active}` (128-133) — a profile has no *content*, so `setProfile @2` selects an opaque backend-defined mode with no way to learn what it will do. This is correct opacity, but a client cannot build a UI without a vocabulary of profile names.

## Recommended actions
1. **Delete the duplicate `ThermalState` and point at power.capnp (or types.capnp) as canonical.** Gain: removes a verbatim duplicate shared with device.capnp. Cost: one reference change.
2. **Collapse the five power-state vocabularies into `T.PowerSleepState` + a lifecycle enum** (`PowerState`'s suspend/hibernate/shutdown/reboot are *lifecycle actions*, not *states*, and conflating them is the root cause). Gain: one answer to "what state is the system in"; the 2046 e-ink/hold-image case becomes expressible. Cost: 3 enum deletions + reference changes; pre-release, ordinal-neutral.
3. **Gate `suspend`/`hibernate`/`reboot`/`shutdown` behind a capability accessor and add an inhibitor/pre-shutdown event.** Gain: a sandboxed app can no longer power off the machine; unsaved-work races get a defined resolution. Cost: one accessor + one subscription (~10 lines).
4. **Fix the structurally-false default in `GridEnergyInfo`** (make `connectionState` optional or add an explicit `unknown @0` variant). Gain: stops a no-inverter system from claiming to be grid-connected. Cost: one field/nullability decision.
5. **Delete the three orphan types** (`IgnitionState`, `SleepState`, `SolarInfo`) or wire `SolarInfo` into a reachable method. Gain: removes dead contract, including a whole solar-monitoring API that nothing can call. Cost: 3 deletions.
6. **Replace `PoEClass` with `T.Voltage`/`T.Current` (or max watts)**, and drop `lldpMedPolicy` to an open token with no protocol implication. Gain: a 2046 PoE class needs no ordinal; non-LLDP backends stop inventing strings. Cost: 2 field changes.
7. **Add subscriptions (or extend `TelemetryConfig`'s sources) for charging, grid, PoE, fuel-gauge, cell-balancing and thermal-risk,** at minimum a coalescing rule on `BatterySubscription`. Gain: removes the polling wakeup pattern that is the file's only eco defect; a carbon widget stops querying the network hourly. Cost: ~6 small subscription interfaces, or one extension of the existing telemetry subscription — prefer the latter (simpler, reuses `TelemetryConfig`).
8. Leave `T.TemperatureKelvin`/`T.Voltage`/`T.Current`/`T.Duration`, `CellBalancingConfig`, `FuelGaugeEstimate`, `Quota`-shaped limits and the whole typed-quantity approach exactly as they are. They are the reason to keep this file, and they are the pattern the other 18 should copy.
