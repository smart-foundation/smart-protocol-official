# audit: `schema/location.capnp` (300 lines)

## Verdict
**KEEP with two targeted fixes.** This is the smallest and one of the soundest schemas in the batch: 300 lines, unit conventions documented in the header (WGS84 degrees, metres, 1-sigma, metres/second, degrees clockwise from true north — location.capnp:12-17), an explicit distinction between ellipsoidal and mean-sea-level altitude (location.capnp:118-120) that most geolocation contracts get wrong, `T.Duration` for the update interval, `T.Pagination` on history and geofence events, `cancel` on the subscription, `GeoFenceGeometry` as a union with a `custom` variant, and — notably — `T.LocationSourceId` promoted into types.capnp. No wire-breakers, no ordinal collisions, no inline bulk payloads. Two real defects: **(1) `attestGeoFence @20 (fenceId, location, privateKey :Data)` asks the caller to pass a private key in the request**, and (2) **`T.LocationSourceId` is an opaque UInt64 that no method can resolve to a name or method**, so `LocationData.source` and `LocationStatus.activeSource` are unreadable — the promotion to types.capnp added the wrapper without the accessor it exists for. Everything else is minor.

## Wire-breakers
- **None.** No compile errors, no ordinal collisions, no undefined references (verified mechanically and by grep).
- `location.capnp:101` — `attestGeoFence @20 (fenceId :Text, location :LocationData, privateKey :Data)`. Not a compile error, but a private key crossing an IPC boundary in a request body is a security defect, and if the underlying transport does not scrub message arenas the key persists in shared memory.

## Doctrine violations
| Rule | `file:line` | What fails | Concrete 2046 failure / cost |
|---|---|---|---|
| R3/R5 | location.capnp:101 | `privateKey :Data` in a request parameter | A private key must never be passed to a service; the service can only misuse it. There is no way to hold the key locally and have the service sign, no key identifier, and no statement of custody. A 2046 key that lives in a secure element cannot be exported at all, so the method is unusable on the most secure hardware. |
| R6 | location.capnp:101-103, 287-299 | `attestGeoFence`/`verifyGeoFenceAttestation` re-implement signature creation and verification, with `GeoFenceAttestation.algorithm @5 :Text` (example `"ecdsa-p256", "ed25519"`) and `signature :Data` | crypto.capnp and signature.capnp are the canonical owners (DESIGN_PRINCIPLES.md:96, Edge Case 4: "reject the mechanism, accept the contract"). A 2046 post-quantum algorithm needs a new string with no negotiation, and two backends' attestations are mutually unverifiable. |
| R4 | location.capnp:134, 155 | `LocationData.source @8 :T.LocationSourceId` and `LocationStatus.activeSource @4 :T.LocationSourceId` | `T.LocationSourceId` is `struct { id @0 :UInt64 }` (types.capnp:670) — opaque. But the semantics are "which positioning **method** produced this location (GPS, Wi-Fi, cell tower, fused, etc.)" (location.capnp:132-133), i.e. a *name*, and there is **no method to resolve an id to a name**. types.capnp:666-669 promoted the type precisely because "location.capnp has no typed source identifier" — and then no accessor was added. Result: every client must display a number. |
| R4 | location.capnp:144 | `LocationData.fingerprint @12 :Data` — "Signal-strength fingerprint for indoor matching" | An opaque inline `Data` blob (hundreds of bytes for a BLE/Wi-Fi fingerprint) carried in every `LocationData`, and therefore in every history entry and every geofence event. No size bound, no version tag, and no method to interpret it. |
| R1 | location.capnp:201-209 | `IndoorMethod {bleBeacon, ultrasound, wifiRtt, magnetic, uwb, hybrid, custom}` | Named technologies (802.11mc is a specific Wi-Fi amendment). Mild — the closed physical methods are plausible — but a 2046 indoor method (UWB-band successor, ambient-scatter) needs an ordinal. |
| R1 | location.capnp:158-165 vs 37-47 | `LocationAccuracy {best, high, medium, low, minimal}` **and** `PrivacyLevel {coarse, fine, exact, none, custom}` | Two 5-value ladders controlling the same continuous quantity (precision), with different value sets, both settable (`setAccuracy @6`, `setPrivacyLevel @14`) and **no rule for their interaction**. A 2046 ranging technology with 1 cm accuracy fits neither ladder. |
| R7 | location.capnp:107-110 | `LocationSubscription.pull @0 () -> (location :LocationData)` — no error, no `ended` | If the position provider is unloaded mid-subscription, pull returns a zero `LocationData` (0,0,0, accuracy 0) — a *plausible-looking* location at null island, which is worse than an error. |

A 2046 client wants one zone concept with accuracy requirements attached. |

## Duplicates & overlaps
- `SpatialPose` (location.capnp:213-222) vs input.capnp:565-570 `SpatialPose` — **identical struct names with different fields** (input's has `position/rotation/velocity/angularVelocity` as `T.Vec3`/`T.T.Quaternion`, same here) — they are in fact field-for-field identical, so one should move to types.capnp; but `LocationData.spatialPose @11 :SpatialPose` (location.capnp:142) refers to the local one, so two schemas now define the same-named type and any consumer importing both gets an identifier clash with no way to know which is meant.
- `GeoFenceCircle.centerLat/centerLon :Float64` (location.capnp:247-248) and `GeoFencePolygon.points @0 :List(T.Vec2)` (253) — a third and fourth geolocation encoding in the batch, against `T.GeoCoordinate` (types.capnp:1441), camera.capnp:494-496, capture.capnp:465-466, display.capnp:704-705.
- `LocationData.source` vs sensor.capnp:257-270 `GnssFix {latitude, longitude, altitudeMeters, accuracyMeters, hdop, vdop, …}` — the GNSS fix is modelled twice, once as a location and once as a sensor type.
- `getHistory @8 (filter :LocationHistoryFilter…)` vs sensor.capnp:364-369 `ContextSnapshot` (also unreachable) — two history shapes.
- `shareLocation @12 (targetDeviceId :T.DeviceId)` vs media.capnp:73 `shareMedia` vs capture.capnp:82 `shareCapture` — three share methods with the same device-tree-id-as-target misuse.

## Gaps & holes
- **No source discovery.** `LocationData.source` is an opaque id with no resolver, so a client cannot learn whether a fix came from GNSS, Wi-Fi or fusion, cannot choose a source, and cannot display provenance. This is the exact gap the `T.LocationSourceId` promotion was meant to close, and it is still open.
- **No subscription overflow or coalescing semantics** (undefined for all subscriptions in the batch; here it matters most because a 10 Hz GNSS stream into a 1 Hz consumer drops silently).
- **No geofence-trigger action model**: `GeoFence.onEnter @2 :Text` / `onExit @3 :Text` (location.capnp:232-233) are free-text action names with no registry, so a 2046 backend and client must agree out of band on the spelling. The same free-text-action anti-pattern as device.capnp's `allowedActions`.
- **No indoor/outdoor transition signal**: `PositioningMode {outdoor, indoor, blended, spatial}` exists (177-183) but there is no event when the mode changes, so a client must poll `getStatus @5`.
- **`setEnabled @3 (enabled :Bool)`** and `setAccuracy @6`/`setPrivacyLevel @14` are global, unscoped, last-writer-wins with no per-app attribution — the same global-settings trap as font.capnp's hinting preference.
- **`floor @9 :Int32`** (location.capnp:138) is documented but no method or event reports a floor change, despite floor changes being the primary indoor signal.

## Zero-cost / eco
- No inline bulk payloads except `fingerprint @12 :Data` (see R4) which is unbounded and carried in every location record.
- **Polling-forcing:** `getLocation @0` is the natural polling target (a 1 Hz UI), and while `subscribeLocation @1` exists, the subscription has no coalescing or minimum-interval rule and no threshold support ("tell me when I move 50 m"). A 2046 navigation client polling at 1 Hz keeps the positioning stack (and often the GNSS radio) continuously awake. A `minDistance`/`minInterval` parameter on the subscription — or a `T.Pagination`-free `pull (maxCount)` with coalescing — removes a first-order battery cost. This is the file's most valuable small change.
- `getLocationsBatch @13` takes `page :T.Pagination`, i.e. offset-into-history, which is correct here (unlike live streams) — a point in its favour.

## UX / implementer guidance
- `LocationData.heading @5 :Float32` uses `NaN` for "unknown or stationary" (location.capnp:126-127). NaN sentinels do not survive every language binding and are not distinguishable from a corrupted value; an explicit optional (or a `Bool valid`) is safer.
- `accuracy @3 :Float32` "1-sigma radius" and `altitudeAccuracy @4` "1-sigma" are well-documented but `LocationHistoryFilter.maxAccuracy @3 :Float32` (282) is named as a *maximum accuracy*, which reads as a *maximum value for the accuracy field*, i.e. a minimum precision requirement. Counter-intuitive naming; rename to `maxAccuracyMeters` (as it is `accuracyMeters` everywhere else).
- `getZoneId`-style accessors are absent: `getAccuracyZone @17 (zoneId :Text)` requires an id the client never receives from any method except `setAccuracyZone @16 → T.VoidResult` (which returns nothing). So an accuracy zone can be set but never read back.
- `GeoFenceEvent.location @4 :LocationData` (location.capnp:262) embeds a full location record (including the fingerprint) inside every geofence event.

## Recommended actions
1. **Remove `privateKey :Data` from `attestGeoFence`** — take a key *identifier* and delegate signing to crypto.capnp/signature.capnp, or delete the method. Gain: removes a private-key-in-request defect and makes attestation work with hardware-backed keys (a secure element **cannot** export a key, so the current signature is unimplementable on the most secure 2046 hardware). Cost: one parameter change or a deletion.
2. **Add a source-discovery accessor** (`listSources @N → List(LocationSourceInfo {id, name, method})`), or replace `T.LocationSourceId` with an open `Text` method token. Gain: `LocationData.source` becomes readable; closes the exact gap the types.capnp promotion was meant to close. Cost: one method (+ one struct) — the cheapest high-value fix in this file.
3. **Add coalescing/minimum-interval (or a distance threshold) to `LocationSubscription`.** Gain: a 1 Hz UI no longer forces the positioning stack and GNSS radio to stay awake at line rate; the batch's clearest eco win after audio's polling and camera's stream. Cost: two optional parameters.
4. **Unify `SpatialPose` with input.capnp** (promote to types.capnp) and use `T.GeoCoordinate` for `GeoFenceCircle`/`GeoFencePolygon`. Gain: removes a same-name different-schema clash and two more geolocation encodings. Cost: one type promotion + reference changes.
5. **Replace `Bool + Text` with `T.Error`** in `verifyGeoFenceAttestation @21` and `readNdef`-style paths; add `ended`/`error` to `LocationSubscription.pull`. Gain: honest failures; a null-island zero value stops looking like a real fix. Cost: result structs.
6. **Rename `LocationHistoryFilter.maxAccuracy` → `maxAccuracyMeters`** and replace the NaN heading sentinel. Gain: removes two naming traps. Cost: comments/one field.
7. **Merge `AccuracyZone` into `GeoFence`** (one zone registry with an accuracy requirement). Gain: two Text-id zone systems become one. Cost: one struct deleted, one field added.
8. Leave `LocationAccuracy`, `PrivacyLevel`, `IndoorMethod`, `PositioningMode`, the altitude/MSL documentation and `setUpdateInterval` alone: each has a `custom` escape, the unit documentation is exemplary, and `setUpdateInterval` is the right eco control.
