# audit: `schema/media.capnp` (424 lines)

## Verdict
**KEEP with targeted fixes.** media.capnp is a small, mostly-clean schema and its payload discipline is already right where it counts: `MediaMetadata.artData @11 :T.DataHandle` with the comment "use buffer handle for images >1KB" (media.capnp:196-197) is the correct pattern, and `SharePreview.thumbnail @3 :T.DataHandle` (media.capnp:320) is correct too. This is the file that audio.capnp's stream path should be compared against. The verdict is KEEP because every defect here is a single structural omission rather than a design error: `PlayerEvent` (media.capnp:140-147) is the only union in the batch's event set with **no `unknown` variant**, five methods return non-result values where failure is real (`transcode @15`, `shareMedia @18`, `createPlaylist @22`, `downloadMedia @19`, `getSharePreview`), the entire transcode-progress contract is dead (`subscribeTranscode @38` takes an id that `transcode @15` never returns), `LyricsData`/`chapters` are unbounded inline lists inside a struct that `listPlayers` ships repeatedly, and `LiveStream`/`StreamHealth` are orphan declarations. No wire-breakers, no ordinal collisions, no enums that leak implementation (this file is one of the few that gets R1 right: `PlaybackStatus`, `RepeatMode`, `SyncType`, `DownloadState`, `CrossfadeCurve`, `LiveInteractionType`, `TranscodeState` are all closed by the semantics of playback and download, and `getSupportedFormats @14 → List(Text)` is the correct open-vocabulary move where a format enum would have been frozen).

## Wire-breakers
- **None.** No compile errors, no ordinal collisions (verified mechanically).
- `media.capnp:114` — `subscribeTranscode @38 (transcodeId :UInt64)`, while `transcode @15 → (transcoded :T.DataHandle)` returns **no id**. `TranscodeProgress.transcodeId @0 :UInt64` (media.capnp:405), `getTranscodeProgress`, and `TranscodeSubscription` therefore reference an identifier that no method produces — dead contract by construction.
- `media.capnp:258-264` — `struct LiveStream {streamUrl, latency, bitrate, viewerCount, streamHealth}` is **referenced by no method** (verified by grep). The header advertises "LiveStream for real-time broadcast with viewer analytics" (media.capnp:22) and no method returns one.

## Duplicates & overlaps
- `getRecommendations @16` vs `getRecommendationsWithScores @26` — two recommendation APIs differing only in payload.
- `setCrossfade @20` vs `setCrossfadeConfig @34`/`getCrossfadeConfig @35`.
- `LyricsData.language @2 :Text` and `MediaMetadata`-level language fields vs `T.Language` (types.capnp:678) — a third and fourth language spelling in the batch (`console.capnp:198` uses `T.Language` correctly).
- `MediaAnalytics` (media.capnp:278-286) vs `getAnalytics @17 (mediaId)` — fine, but the "analytics" concept overlaps device.capnp's `getResourceUsage` and print.capnp's `PrintAccounting`.
- `shareMedia`/`shareCapture`/`shareLocation` (three identical shapes).
- `DownloadStatus` vs print.capnp's `PrintJob` (both are job-progress structs with `state`, `progress`, and no shared job model).

## Gaps & holes
- **No read path for a `MediaPlayer`'s audio frames** — media.capnp is a *control* schema (play/pause/seek/volume), which is correct division of labour with audio.capnp, but `openUri @12 (playerId, uri :T.Uri)` does not state whether the player consumes the URI itself or delegates to audio.capnp, nor who owns the network stack. A 2046 client with a custom transport cannot supply frames.
- **No playback error surface at all.** There is no `PlayerEvent.playbackError`, no `T.Error` on any player method, and `PauseJob`-style failure paths are `T.VoidResult` only. A mid-stream network failure has no representation — the client sees the state stay `playing` forever.
- **No queue/playlist bounds**: `addToPlaylist @23` adds one item at a time with no bound check and no `total` on the playlist (a playlist id is a `UInt64`, and there is no `listPlaylists`).
- **`listDownloads @29` is paginated but `getDownloadStatus @28` takes `UInt64` with no ownership check** — any client can read any other client's download status.
- **No history/recency contract**: `getAnalytics @17` reports a count and `lastPlayed`, but `MediaItem` has no timestamps, so "recently played" ordering is per-backend.

## Zero-cost / eco
- **Correct:** `artData @11 :T.DataHandle` and `SharePreview.thumbnail @3 :T.DataHandle` (media.capnp:197, 320) — bulk payloads are buffer references. `openUri @12 (uri :T.Uri)` avoids passing media bytes at all. This file passes R2.
- `LyricsData`/`chapters` — unbounded inline lists (see R2 above). Copy cost scales with content length and is re-paid on every `getMetadata`/`listPlayers`.
- **`getPosition @9 (playerId) → (position, duration)`** is the natural polling target for a progress bar. `subscribePlayer @13 → PlayerSubscription.pull → List(PlayerEvent)` exists and carries `positionChanged @2`, so the event path is present — but the events are unbatched and unthrottled, and the subscription carries the *whole* `MediaMetadata` on every `metadataChanged`, so a client that only wants position must filter. Adding a `minInterval`/threshold to the subscription (or splitting `positionChanged` into its own subscription) removes the polling temptation.
- `MediaPlayer` is returned by `listPlayers @0` (paginated) and embeds the full `metadata` — so listing players ships every player's full metadata including lyrics, chapters and artwork handle.

## UX & implementer guidance
- `getPlayer @1 → MediaPlayer` and `subscribePlayer @13` exist, but there is **no `T.Error` on any player method** — a `seek @7` beyond duration returns `T.VoidResult.success` and does nothing (no clamping rule).
- `MediaPlayer.identity @2 :Text` (media.capnp:154) is undocumented — is it a bus name, a D-Bus-ish unique name, a package id? An implementer cannot fill it in without guessing.
- `TranscodeProgress.state @3 :TranscodeState` and `DownloadStatus.state @5 :DownloadState` are two near-identical state ladders (`queued`/`processing`/`completed`/`failed`/`cancelled` vs `pending`/`downloading`/`paused`/`completed`/`failed`/`cancelled`) with no shared supertype.
- `schedulePrint`-style scheduling does not exist here, but `setCrossfade @20` (duration-only) and `setCrossfadeConfig @34` (curve/gapless/volumeAdjust) differ in what they can express, so a client using the older ordinal can never enable gapless playback.

## Recommended actions
1. **Add `unknown @N :UnknownEvent` to `PlayerEvent`.** Gain: the one union in the batch missing the doctrine's mandatory forward-compat variant; new player event types become addable. Cost: one variant + one `UnknownEvent` struct (the shape is already in ai.capnp:533-536).
2. **Add `T.Error` to `transcode` (return `transcoded :T.DataHandle` + `error :T.Error`, or a result union), `shareMedia`, `createPlaylist`, `downloadMedia`.** Gain: a failed transcode stops looking like an empty output; a failed share stops looking like an empty link. Cost: result structs.
3. **Fix the transcode-id dead end**: have `transcode @15` return a `transcodeId`, or delete `subscribeTranscode @38`/`TranscodeProgress`. Gain: either progress reporting works or the contract stops advertising a feature it lacks. Cost: one field.
4. **Move `lyrics` and `chapters` out of `MediaMetadata`** into on-demand fetches (`getLyrics (mediaId)`, `getChapters (mediaId)`), or return `List` handles. Gain: `listPlayers`/`getMetadata` stop re-shipping unbounded content; an 800-chapter audiobook no longer costs 800 structs per call. Cost: two methods, one field removed.
5. **Type the three `UInt64` id spaces** (`downloadId`, `playlistId`, `transcodeId`) the way `T.MediaItemId` was typed. Gain: a client stops mixing id spaces. Cost: three typed wrappers in types.capnp.
6. **Stop trusting caller-supplied identity**: take `senderId`/`timestamp` from the transport, not from `LiveInteraction`; add ownership checks on `getDownloadStatus`/`pauseDownload`. Gain: one app can no longer act or read as another. Cost: two field removals + a rule.
7. **Add a `minInterval` (or distance threshold) to `PlayerSubscription` and split position from metadata.** Gain: a progress bar stops polling `getPosition` and stops receiving full metadata per frame. Cost: two parameters.
8. Leave `PlaybackStatus`, `RepeatMode`, `SyncType`, `DownloadState`, `CrossfadeCurve`, `LiveInteractionType`, `TranscodeState`, `MediaType`-style open format lists and the `T.DataHandle` artwork alone: this is the file's best behaviour and converting it to open tokens would add machinery without removing any.
