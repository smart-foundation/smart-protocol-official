# audit: `schema/screenlock.capnp` (385 lines)

## Verdict
**KEEP with targeted fixes.** screenlock.capnp is small, focused and mostly well-formed: `T.Duration` throughout the idle policy, `T.AppId` for application identity, `T.Error` in the failure path (audit-3), `custom` variants on every union, an explicit `CustomLockEvent {typeId, payload}` (screenlock.capnp:209-212) that is the doctrine-exact unknown-event shape, and a header that states its own ownership claim plainly. On the flagged question: **the `UnlockCredential` ownership conflict with session.capnp is already resolved in the current revision** — there is exactly one `UnlockCredential` definition in the repository (screenlock.capnp:140) and session.capnp:37 imports it as `Screenlock.UnlockCredential`, with both files documenting the arrangement (screenlock.capnp:8-9; session.capnp:10-11,14). Canonical home: **screenlock.capnp**. Do not "fix" what is already fixed. The real residual conflicts are different and worth fixing: `lock`/`unlock` exist in **both** schemas with different result types (`T.VoidResult` vs `UnlockResult`), idle management exists in **both** (`IdlePolicy` vs `setIdleTimeout`), both files declare an `interface Session` with the same name, and the Audit-7/9 feature sweep (widgets, hostile environment, duress, step-up, wearable presence, pattern/face/voice/trusted-device config) has drifted into configuration-by-parameter for hardware features that a 2046 lock screen may not have.

## Wire-breakers
- **None.** No compile errors, no ordinal collisions (verified mechanically).
- `screenlock.capnp:161-175` — `UnlockResult` carries **two deprecated variants (`failed @1 :UInt32`, `lockedOut @2 :UInt32`) alongside their typed replacements (`failedError @4 :T.Error`, `lockedOutDuration @5 :T.Duration`)**, so a client must handle both and a backend may set only one. The header's audit-3 note (screenlock.capnp:18-19) describes exactly this. Pre-release, the deprecated pair should be deleted rather than preserved (DESIGN_PRINCIPLES.md:340 says preserve ordinals for wire compatibility — but there is no released wire to be compatible with, and this schema is slated for a "revamp before first release").
- `screenlock.capnp:37` — `interface Session` here and `interface Session` in session.capnp:35. Two top-level types with the same name in two schemas. In Cap'n Proto they are scoped (`screenlock.Session` vs `session.Session`), so it compiles — but DESIGN_PRINCIPLES.md:213 already flags six `Session` interfaces, and this is the seventh with no distinguishing suffix, so any consumer that imports both unqualified gets an ambiguity.

## Duplicates & overlaps
- `UnlockCredential` — **resolved**: one definition (screenlock.capnp:140), imported by session.capnp:37. Canonical home confirmed; no action needed.
- `lock`/`unlock`/idle management — duplicated with session.capnp (above).
- `interface Session` — a seventh same-named interface (DESIGN_PRINCIPLES.md:213 counts six; screenlock makes seven, and font.capnp adds an eighth via `FontSession` — different name, same pattern).
- `LockScreenNotification` vs notification.capnp's notification model.
- `TrustedDeviceType {bluetooth, nfc, uwb, wifi}` vs bluetooth.capnp's transport/profile enums and nfc.capnp's transport concepts.
- `HandshakeRequest/HandshakeResponse/HandshakeResult` — duplicated with font.capnp:53-70 (and the batch-wide session handshake).
- `BiometricStepUp`/`secondaryMethod :Text` (screenlock.capnp:251-256) vs auth.capnp's MFA model — a step-up method as a free-text name.

## Gaps & holes
- **No unlock-attempt feedback contract on the lock screen.** `unlock @2` returns `UnlockResult`, but nothing tells a *lock screen application* (distinct from the caller) that an attempt happened, so a UI cannot show "wrong PIN, 2 of 5 attempts left" without polling `isLocked @3`/`getSecurityPolicy @14`.
- **No relation between `IdlePolicy.suspendOnIdle` and power.capnp's `suspend @4`.** Two suspend paths (the session's idle policy and the power service's explicit call) with no precedence and no inhibitor coordination (power.capnp has no inhibitor at all — see the power audit).
- **No hostile-environment escalation semantics.** `reportHostileEnvironment @15 (signal :HostileEnvironmentSignal)` with `signalType :Text`, `confidence :Float32`, `triggerSource :Text` reports a signal with no defined vocabulary, no threshold, and no stated consequence (lock? wipe? alert?) — so a 2046 theft-detection feature has to invent both the signal names and the response.
- **No duress-credential semantics.** `DuressCredential {marker, silentAlert, notifyContact}` (244-248) declares *flags* but no method describes what a duress unlock *does* (silent alarm to whom? which contact? with what payload?). The contract declares capability without behaviour, so every backend implements a different safety story — the highest-stakes fork in this file, because a coercion victim's safety depends on it.
- **No step-up timeout handling**: `BiometricStepUp.stepUpTimeout :T.Duration` exists but no event when it expires.
- **`inhibitIdle @7 (reason :Text) -> (handle :T.InhibitHandle)`** uses the shared `T.InhibitHandle` (good), but there is no way to list active inhibitors, so a 2046 debugger cannot tell why the screen will not dim.
- **`getPatternLockConfig @22` returns `PatternLockConfig.patternHash @5 :Data`** (screenlock.capnp:294) — a *hash of the user's pattern* readable through an ungated method. Even hashed, returning it lets a client test offline guesses, and it contradicts the opacity principle's intent.

## Zero-cost / eco
- No inline bulk payloads, no unbounded lists, no polling-forcing patterns. `IdlePolicy` (screenlock.capnp:179-185) is exactly the right shape for an eco-critical concern: explicit timeouts so a device can sleep rather than poll, and `inhibitIdle`/`uninhibitIdle` is the correct inhibitor pattern.
- **Idle-power:** `LockEventStream.next @0` (189-190) blocks rather than polls, so a lock screen does not wake the CPU — good. The one gap is that the idle-event source is a *push* on the service with no minimum-interval rule, so `idleChanged` (199) can fire at second granularity.
- `subscribe` returns `LockEventStream` (stream pattern) rather than a pull subscription; converting is cheap and would let a lock screen coalesce events rather than block in `next`.

## UX / implementer guidance
- `UnlockResult` has two deprecated and two typed variants with the comment "New code should prefer failedError @4 and lockedOutDuration @5" (screenlock.capnp:157-159). A 2046 implementer cannot tell whether setting only the deprecated pair is an error.
- `HandshakeResponse.result @1 :HandshakeResult` plus `HandshakeResponse.sessionId @0 :T.SessionId` — a handshake that returns a session id even when `result = rejected`, with no statement of whether the id is usable.
- `FaceUnlockConfig.timeoutMs @6 :UInt32` and `VoiceMatchConfig.timeoutMs @7 :UInt32` use raw milliseconds while every other duration in the file is `T.Duration` — an inconsistency inside a single file.
- `LoyaltyProgram`-style configuration methods in other schemas have the same shape here: `get*Config`/`set*Config` pairs that return whole structs with no `T.Error` and no per-actor scoping.
- `IdleChangedEvent.duration @1 :T.Duration` (206) is ambiguous — the time since idle, or the configured timeout? The name suggests one and the type suggests either.

## Recommended actions
1. **Consolidate lock/unlock and idle into session.capnp (or here — pick one).** The cleanest split: `session.capnp` owns `lock`/`unlock`/`isLocked` (it is the session authority) and `screenlock.capnp` owns `IdlePolicy` and the lock-screen surface; then `Session.unlock` must return `Screenlock.UnlockResult` rather than `T.VoidResult`, and `Session.setIdleTimeout` must be removed in favour of `IdlePolicy`. Gain: one lock contract and one idle contract, with the richer result type everywhere — removes the "two paths that must agree forever" hazard. Cost: one signature change and one method deprecated; these are directly adjacent files and both are pre-release.
2. **Delete the deprecated `failed @1 :UInt32` and `lockedOut @2 :UInt32`** from `UnlockResult`. Gain: one failure representation; a backend can no longer set only the deprecated pair. Cost: two ordinals — free pre-release.
3. **Gate the sensitive half**: ungated `isLocked`; capability-gated `unlock`, `setSecurityPolicy`, `setPatternLock`, `setFaceUnlockConfig`, `setVoiceMatchConfig`, `setTrustedDeviceConfig` (ai.capnp:578-584). Gain: a sandboxed app can no longer weaken the lock policy. Cost: an accessor layer.
4. **Specify duress semantics** (what a duress unlock does, and to whom a silent alert goes) or delete `DuressCredential`. Gain: a coercion victim's safety stops being a per-backend invention; this is the highest-stakes fork in the file. Cost: a short behavioural section, or a deletion.
5. **Stop returning `patternHash`** from `getPatternLockConfig @22`. Gain: removes an offline-guess surface through an ungated method. Cost: one field removed.
6. **Rename one of the two `Session` interfaces** (`LockSession`, matching the batch's `CompositorSession` precedent in DESIGN_PRINCIPLES.md:213). Gain: removes the seventh same-name collision. Cost: a rename.
7. **Convert `LockEventStream` to the canonical pull + cancel pattern** (and add a minimum-interval/coalescing rule). Gain: one subscription pattern batch-wide; a lock screen can batch events instead of blocking. Cost: two method signatures.
8. **Move lock-screen widgets to surface/compositor and lock-screen notifications to notification.capnp** (delegation, per DESIGN_PRINCIPLES.md:218). Gain: removes two duplicated subsystems and the `permissions :List(Text)` string list. Cost: two methods deleted.
9. Leave `UnlockCredential`'s canonical home, `T.Duration` usage, `IdlePolicy`'s shape, `CustomLockEvent` and the `T.Error`-typed failure path alone: the ownership resolution is done, and those are the file's strongest parts.
