# audit: `schema/framebuffer.capnp` (596 lines)

## Verdict
**FIX (targeted).** framebuffer.capnp is the strongest zero-copy design in this batch and should be protected, not rewritten: pixels travel as `SharedMemoryRegion` references (framebuffer.capnp:63, 103), the ICC/colour-management LUT is a `T.DataHandle` (framebuffer.capnp:519), and the file deliberately offers `properties :List(KeyValue)` so that "DRM-vs-other vendor coupling" is avoided (framebuffer.capnp:75-77). That is exactly right, and it is the reason the display/camera/audio schemas should look at this one. The defects are a **structurally empty atomic contract** (`testAtomic @4 ()` and `commitAtomic @5 ()` take no configuration at all — the entire KMS atomic-test model cannot be expressed), one missing forward-compat variant on `FramebufferEvent`, three duplicate vocabularies with types.capnp (`FramebufferColorSpace`, `DisplayRotation`, `DpmsState`), a dangling `DisplayModeFlags` reference, and one Linux/VFIO noun in a required field. Targeted fix.

## Wire-breakers
- **No compile errors, no ordinal collisions** (verified mechanically).
- `framebuffer.capnp:292-295` — `testAtomic @4 () -> (result :AtomicTestResult)` and `commitAtomic @5 () -> (result :T.VoidResult)` take **zero parameters**. The comments ("Test an atomic configuration without committing it", "Commit an atomic configuration") describe an operation whose input cannot be passed. The only configuration channel in the whole interface is the set of per-framebuffer setters (`setColorManagement`, `setSyncMode`, `setRotation`, `setScaling`, `setDpmsState`, `setHdr10Plus`). So a compositor backend cannot stage → test → commit a mode set; it must call six setters and hope.
- `framebuffer.capnp:873` (in display.capnp's `ModeSpec`) — `DisplayModeFlags` referenced from a comment but defined nowhere. Cited here because it is the display/framebuffer boundary and the same dangling reference breaks `ModeSpec.flags`.

## Duplicates & overlaps
- `DpmsState` ≡ display.capnp:359. `FramebufferColorSpace` ≡ `T.ColorSpace` ≡ display.capnp `ColorSpace`. `DisplayRotation` ≡ `T.SurfaceTransform`/`T.BufferTransform`. `SyncMode` ≡ display.capnp `AdaptiveRefreshPolicy` ≡ `T.DisplayRefreshMode`.
- `HdrInfo.maxLuminance/minLuminance/maxFrameAverage/maxContent :UInt32` (framebuffer.capnp:378-381) vs display.capnp:668-673 `HdrCapabilities {maxCllRange :T.Vec2, fallRange :T.Vec2}` — one models CLL/FALL as bare UInt32 fields, the other as `T.Vec2` ranges (a misuse of a 2D vector type for a range pair). Two representations, neither typed for luminance.
- `FrameTimingInfo.refreshRate :UInt32` (framebuffer.capnp:535), `SyncInfo.refreshRate/minRefreshRate/maxRefreshRate :UInt32` (419-421) and `DisplayMode.refreshRateMilli :UInt32` (187) are a fourth/fifth/sixth refresh-rate encoding; `T.Frequency` exists (types.capnp:788).
- `Hdr10PlusMetadata.maxscl :List(UInt32)`, `distributionMaxrgbPercentile :List(HdrPercentile)`, `bezierCurveAnchor :List(UInt16)` (framebuffer.capnp:585-589) — per-frame dynamic metadata, but the only channel is the one-shot setter `setHdr10Plus @24`. Per-frame data through a state setter is a design mismatch (see Zero-cost).
- `AtomicTargetKind` (framebuffer.capnp:268-275) duplicates the union it labels: `AtomicTargetId` already discriminates framebuffer/plane/crtc, so a rejection carries both an untagged kind enum and a tagged union.

## Gaps & holes
- **The atomic contract has no input.** See Wire-breakers. This is the single largest hole in the file: `testAtomic`/`commitAtomic` are the entire reason a framebuffer service exists at the driver boundary (stage, validate, commit without tearing), and they cannot be called. Demonstrated fork risk: each backend will invent an out-of-band configuration channel, and two backends' atomic semantics will not compose.
- **No page-flip / vsync completion contract.** `SyncInfo` describes the mode but there is no fence, no "flip done" event, and `FramebufferEvent` has no frame-timing variant. A compositor cannot implement double-buffered presentation without inventing its own sync primitive.
- **No cursor-plane ownership.** `CursorPlane` (framebuffer.capnp:98-104) is a *struct* with a `pixelRegion`, and `cursors :List(CursorPlane)` is embedded in `Framebuffer` — but there is no method to set the cursor position or image, so the hardware cursor is described and unusable.
- **No mode-set error taxonomy.** `AtomicRejection.reason :T.Error` exists (good), but nothing states which reasons are authoritative (a rejected pixel clock vs a rejected bandwididth vs a framebuffer-too-large), so a client cannot map a `reason` to a fallback action.
- **No `attach`/`detach` lifecycle for a framebuffer beyond `active :Bool`** — a driver that detaches mid-presentation is indistinguishable from one that was never active.

## Zero-cost / eco
- **Correct, and worth copying:** `Framebuffer.region :SharedMemoryRegion` and `CursorPlane.pixelRegion` are buffer references — the pixel payload is never copied (framebuffer.capnp:63, 103). `ColorManagement.lut` and `IccProfile.data` are `T.DataHandle` (519, display.capnp:539). `exportRecording`-style whole-blob returns do not exist here. This file is the batch's model for R2.
- `Framebuffer.clut :List(ColorEntry)` (framebuffer.capnp:70) — a 256-entry CLUT is ~1.3 KB, and `list @0` ships a CLUT per framebuffer. Bounded and rare: not worth changing.
- **Idle-power trap:** `setHdr10Plus @24` is a per-frame metadata setter with no batching. A backend implementing dynamic HDR must accept one RPC per displayed frame (60-120/s) — or buffer and coalesce, which the contract does not permit or forbid. This is a genuine eco cost on video playback: the hot path has no streaming/queue channel.
- `getFrameTiming @17`, `getSyncInfo @11`, `getPlaneBlending @16`, `getAntiAliasingInfo @15` are per-framebuffer getters with no caching or batching; a client measuring frame pacing will poll.

## UX & implementer guidance
- `Plane.rect`/`srcRect`/`Crtc.mode` use `T.Rect` and `DisplayMode` while `DisplayMode.pixelClockMilliHz :UInt64` documents "Pixel clock in Hz × 1000 (so 60000 = 60 MHz)" (framebuffer.capnp:174-175) and `refreshRateMilli @9` documents "× 1000 (so 60.001 Hz → 60001)". Two milli-scaled quantities with correctly-stated units but no typed wrapper — `T.Frequency` exists.
- `DisplayScaling.hidpi @2 :Bool` (framebuffer.capnp:579) — a HiDPI boolean is a 2010-era UI concern inside a scanout contract; a backend must decide what it means for a 600 ppi panel.
- `AntiAliasingInfo.lcdFilter @4 :Bool` and `filter @2 :Text` (framebuffer.capnp:476-482) are ClearType/FreeType-specific, the header's own words ("for ClearType/FreeType"), in a file claiming no rasterizer assumptions.
- `AtomicRejection` carries **three** target references (`target :AtomicTargetKind`, `targetId :UInt64`, `typedId :AtomicTargetId`) with a comment saying "Prefer typedId for new consumers" — three spellings of one reference where one would do.

## Recommended actions
1. **Give the atomic methods an input**: add `AtomicRequest` carrying the property sets to check/commit, using the already-existing `AtomicTargetId` union as the target reference. Gain: makes `testAtomic`/`commitAtomic` performable at all; removes the largest fork risk in the file; activates the `AtomicTargetId` scaffolding that is currently dead. Cost: one request struct + one parameter on two methods (both `()` today, so ordinal-neutral).
2. **Add `unknown @N :UnknownEvent` to `FramebufferEvent`.** Gain: forward-compatible hotplug/mode events; matches the doctrine shape every other union in this batch is supposed to have. Cost: one variant.
3. **Delete `FramebufferColorSpace`, `DisplayRotation`, `DpmsState` in favour of `T.ColorSpace`, `T.SurfaceTransform`, `T.PowerSleepState`.** Gain: collapses three duplicate vocabularies (and the DPMS verbatim pair with display.capnp); a 2046 display without DPMS states becomes expressible. Cost: three type-reference changes.
4. **Remove `vfioGroup` (make it `properties :List(KeyValue)`, which the file already has).** Gain: a non-Linux GPU backend no longer invents a number for a required field. Cost: one field moved to the open property bag.
5. **Rename `Crtc` → a transport-neutral term** (e.g. `ScanoutEngine`/`OutputPipeline`) and `T.CrtcId` with it. Gain: removes the CRT noun; the 2046 AR/pipeline case needs no fiction. Cost: a repo-wide rename of a shared type — largest cost in this list, so rank it last and only if the rewrite wave is already touching types.capnp.
6. **Add a page-flip/fence contract** (a flip-completed event or a fence handle). Gain: compositors can implement double buffering without inventing sync. Cost: one event variant or one `T.FenceHandle`-typed field (the type exists, types.capnp:943).
7. **Define `DisplayModeFlags` or replace `flags @5 :UInt32` with `List(DisplayFlag)`.** Gain: removes the dangling reference at display.capnp:873. Cost: one type.
8. Leave `Hdr10PlusMetadata`, `SubpixelLayout`, `EotfTransfer` and the milli-scaled fields alone: each is a documented, bounded wart whose fix costs more ordinals than it buys correctness pre-release.
